# Forge Should Own Deep Review Semantics
**Forge should adopt neither LangGraph nor LangChain in the production core now, and it should not adopt GraphRAG, Graphify, or another general graph system for single-PRD review.** The immediate architecture should be a Forge-owned, source-span-first claim ledger projected into a small typed graph, followed by deterministic candidate generation, constrained model classification, mechanical evidence verification, and template-rendered findings. This design directly serves the primary experience: show what prevents correct implementation, where the PRD conflicts with itself, and which decision the author must make, while keeping the existing readiness score as a separate deterministic audit. LangGraph deserves a later, bounded orchestration spike because its checkpoints, interrupts, parallel execution, and failure recovery map to a growing review workflow, but it must prove net code deletion without replacing Forge's identity, idempotency, evidence, or scoring contracts ([LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence); [Forge D-045](https://github.com/amanchawla-wynk/forge/blob/main/docs/DECISIONS.md#d-045-make-evidence-backed-deep-review-the-primary-experience)). LangChain should remain optional and adapter-scoped because its strongest conveniences assume an application-owned model invocation, whereas Forge core borrows inference from an MCP client or accepts agent-produced structured output ([LangChain structured output](https://docs.langchain.com/oss/python/langchain/structured-output); [Forge architecture](https://github.com/amanchawla-wynk/forge/blob/main/docs/ARCHITECTURE.md#inference-modes)). A 20-100 page PRD is large enough to benefit from graph-shaped analysis but too small, static, and evidence-sensitive to justify embeddings, community summaries, a graph database, or a persistent memory platform. The target is therefore **Forge domain semantics first, a replaceable in-process graph second, optional LangGraph orchestration only after measurement, and no general GraphRAG stack unless the product later expands to multi-document retrieval or portfolio analysis**.

## Deep review depends on preserved claims, not agent autonomy

The principal architecture problem is representation loss, not insufficient model agency. Forge's current extraction path verifies batch fragments and then selects one satisfied candidate per rubric field; its score path subsequently exposes one run associated with the modal criterion verdict. That is appropriate for deterministic readiness scoring, but it discards the multiple statements needed to discover cross-section disagreement ([Forge batch extraction](https://github.com/amanchawla-wynk/forge/blob/main/src/forge/extract/batch.py); [Forge scoring engine](https://github.com/amanchawla-wynk/forge/blob/main/src/forge/score/engine.py)). More model calls, an agent loop, or retrieval over the same consolidated representation would not recover a skip threshold, timeline, ranking rule, or fallback that has already been collapsed away. **The first deep-review deliverable must therefore be an immutable claim ledger built before score-oriented consolidation.**

The ledger should distinguish a `ClaimOccurrence`, meaning one uniquely located source assertion, from a `ClaimInterpretation`, meaning one extraction run's bounded parse of that assertion. A source occurrence needs an identity derived from the source hash, block identity, quote-local offsets, and exact quote; this keeps identical sentences in different sections distinct while deduplicating repeated extraction of the same span. Each interpretation should carry only analysis-relevant attributes such as claim kind, subject, property, polarity, modality, scope, phase, conditions, and typed numeric or temporal values. Every source-derived string must remain either an exact substring or a deterministic normalization of the quote. This follows Forge's existing rule that evidence must be mechanically found in the complete normalized document, and it closes the current ambiguity in first-match quote lookup when text repeats ([Forge scoring theory](https://github.com/amanchawla-wynk/forge/blob/main/docs/SCORING_THEORY.md#evidence-rule)).

Reconciliation should happen attribute by attribute across independent run indexes. A modal value can become the working interpretation; a tie or lack of majority becomes `unknown`, while all observed alternatives and agreement remain available for audit. Different source spans should never be merged in ledger storage. They may instead receive advisory graph relations such as `restates`, `equivalent_to`, or `possibly_same_subject`. This separation matters because repeated model observations are not additional source facts, and model disagreement about a span's meaning is not itself a PRD contradiction. Document-level inference research reinforces the distinction between relation labels and supporting spans: ContractNLI jointly evaluates entailment-style relations and evidence spans, while FEVER likewise requires both a claim decision and supporting evidence rather than treating label accuracy alone as sufficient ([ContractNLI](https://aclanthology.org/2021.findings-emnlp.164/); [FEVER](https://aclanthology.org/N18-1074/)).

The graph should then be a **projection of verified ledger facts, never a second extraction corpus**. It should connect claim occurrences to typed nodes for requirements, actors, entities, states, metrics, events, dependencies, milestones, phases, definitions, and sections. Deterministic indexes should block candidate comparisons by shared subject/property, metric or event identity, dependency, milestone, explicit cross-reference, or precedence relation, avoiding an indiscriminate all-pairs comparison. Python may confirm only mechanically provable defects: opposite polarity under exactly compatible scope, disjoint normalized values or ranges, impossible arithmetic, incompatible exact dates, precedence cycles, duplicate ranks, broken references, missing formula operands, or explicit supersession whose older rule remains active. Everything involving paraphrase, referent identity, overlapping scope, implied exception, intended precedence, suspected staleness, or semantic computability must remain a closed-set classification over pre-enumerated candidates. HANS demonstrates why lexical overlap cannot be accepted as proof of entailment or contradiction, even for strong inference models ([HANS](https://aclanthology.org/P19-1334/)).

The output contract should preserve that epistemic split. A `ConsistencyLedger` should retain every candidate and its outcome, including compatible, unclear, rejected, and verification-failed rows; user-facing findings should be a deterministic projection of publishable rows. Each finding should contain two or more reverified spans for a conflict, one span for a unary ambiguity, a versioned finding type, verification status, scope relation, affected consumers, implementation effects, model agreement, and immutable analysis provenance. **No model should author the consequence or requested decision.** Python should render both from versioned templates populated only with verified values and fixed enums, preserving Forge's existing closed-output approach ([Forge D-035](https://github.com/amanchawla-wynk/forge/blob/main/docs/DECISIONS.md#d-035-guardrailed-closed-set-contextualization-of-remediation-questions)). Until human validation exists, ordering should be an exposed expert-prior tuple such as deterministic impossibility, normative conflict, failed-gate overlap, affected-consumer count, cross-section status, and stable ID, labelled `review_order` rather than severity or risk.

## LangGraph must earn adoption; LangChain should stay outside core

LangGraph maps credibly to the future workflow. `StateGraph`, conditional edges, checkpoints, `thread_id`, interrupts, retries, state history, fan-out, and pending writes could coordinate initial extraction, claim analysis, candidate classification, human decisions, answer-delta checkpoints, revision approval, and final verification ([LangGraph checkpoints](https://docs.langchain.com/oss/python/langgraph/checkpointers); [LangGraph interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)). The natural mapping is `review_session_id` to `thread_id`, Forge's typed review state to graph state, and each expensive inference or artifact operation to an isolated node. This becomes compelling if deep review introduces parallel classifiers, background work, partial-failure recovery, multiple approval roles, or branchable investigations.

That feature overlap does not justify migration today. Forge already has a working local SQLite state machine with exact-document discovery, explicit resume, source/rubric/workspace/user binding, optimistic `session_version`, request-digest-bound `operation_id`, operation reservation, cached retry results, expiry, deletion, and semantic events ([Forge D-042](https://github.com/amanchawla-wynk/forge/blob/main/docs/DECISIONS.md#d-042-forge-owns-review-identity-and-new-chats-resume-explicit); [Forge D-043](https://github.com/amanchawla-wynk/forge/blob/main/docs/DECISIONS.md#d-043-harden-durable-review-integrity-before-expanding-scope)). A LangGraph checkpoint is a historical runtime snapshot, not the externally visible compare-and-swap token for one authoritative review head; a graph execution ID is not a caller-stable idempotency key. Official documentation reviewed in the notes does not establish a built-in equivalent to Forge's request-bound operation ledger or an atomic transaction spanning graph checkpoints and Forge's session, operation, and event records ([LangGraph checkpointer interface](https://docs.langchain.com/oss/python/langgraph/checkpointers#checkpointer-interface)).

Replay semantics create the sharpest risk. Resuming an interrupt restarts its node from the beginning, downstream replay executes model and API calls again, and `update_state` creates a branch rather than rolling history back ([LangGraph interrupt rules](https://docs.langchain.com/oss/python/langgraph/interrupts#rules-of-interrupts); [LangGraph time travel](https://docs.langchain.com/oss/python/langgraph/use-time-travel)). Without Forge's reservation and idempotency envelope, this can duplicate borrowed inference charges, append answers twice, recreate revision files, or make a runtime retry look like an independent extraction run. If LangGraph is adopted, one interrupt must correspond to one stable question identity, side effects must live in successor nodes, inference results must be committed under the original operation and run identity, user-facing time travel must remain disabled, and the Forge session head must remain authoritative. Persistence replacement should be a separate decision after orchestration parity, not part of the first migration.

LangChain has a narrower fit. Its structured-output strategies, validation retries, model middleware, and tool abstractions help when an application owns a compatible chat-model object ([LangChain structured output](https://docs.langchain.com/oss/python/langchain/structured-output); [LangChain tools](https://docs.langchain.com/oss/python/langchain/tools)). Forge's primary MCP path deliberately does not own provider credentials or instantiate provider models, and the agent-driven fallback performs inference outside the Forge process. An internal LangChain agent deciding which tools to call would add discretion where Forge intentionally uses deterministic routing and closed-set model tasks. **LangChain should not become a core dependency or domain boundary.** A separately packaged dashboard experiment may compare its structured-output negotiation and retry behavior with the existing LiteLLM/Pydantic adapter, but only if it remains within the optional dashboard boundary and demonstrates better reliability or less adapter code. LangSmith should likewise remain off by default because its standard observability path requires an account and API key and can carry prompts, state, and tool activity ([LangSmith observability](https://docs.langchain.com/langsmith/observability)).

## One PRD merits a graph, not GraphRAG

A 20-100 page PRD contains enough cross-references and repeated requirements to benefit from graph-shaped analysis, but **data volume alone does not justify a graph system**. The decisive questions are whether Forge needs relevance retrieval, community discovery, temporal memory, shared persistence, or graph-database query capabilities. For one static document, it needs none of them. It needs exhaustive source eligibility, exact-span provenance, typed one- and two-hop joins, candidate generation, and auditable relation classification. An in-process typed adjacency structure can provide those capabilities; NetworkX `MultiDiGraph` is a replaceable implementation option if parallel attributed edges and traversal utilities save meaningful code ([NetworkX MultiDiGraph](https://networkx.org/documentation/stable/reference/classes/multidigraph.html)).

Microsoft GraphRAG can technically process a singular large document, but its architecture extracts entities and relationships, builds a Leiden community hierarchy, generates community summaries, and provides global, local, DRIFT, and vector-oriented query modes ([Microsoft GraphRAG overview](https://microsoft.github.io/graphrag/)). Microsoft estimates graph extraction at roughly 75% of standard indexing cost, and even FastGraphRAG trades cost for a noisier graph aimed primarily at global summary questions ([GraphRAG indexing methods](https://microsoft.github.io/graphrag/index/methods/)). Those stages solve holistic corpus question answering, not exhaustive comparison of source-bound requirement atoms. Generated relationship descriptions and community reports also lack Forge's mandatory exact-quote verification contract. GraphRAG should therefore be rejected for the single-PRD production path.

Graphiti and Cognee are farther from the requirement. Graphiti is designed for dynamic, frequently updated data with episodes, temporal validity, invalidation, embeddings, and a graph backend; Cognee is a persistent agent-memory platform spanning documents, code, conversations, relational provenance, vectors, and graphs ([Graphiti overview](https://help.getzep.com/graphiti/graphiti/overview); [Cognee architecture](https://docs.cognee.ai/core-concepts/architecture)). A versioned PRD does not gain enough from temporal memory or multi-store recall to justify those operational and trust boundaries. Their provenance concepts are useful references, but neither documents Forge's full guarantee that every displayed assertion is bound to an exact span mechanically found in an exhaustively processed source.

Graphify is the closest conceptual reference because it is local, uses NetworkX, avoids vector retrieval, labels relations by confidence class, and emits inspectable JSON and graph reports ([Graphify repository](https://github.com/Graphify-Labs/graphify); [Graphify architecture](https://github.com/Graphify-Labs/graphify/blob/v8/ARCHITECTURE.md)). It still targets whole projects and adds file discovery, multi-format extraction, clustering, reporting, exports, caching, semantic orchestration, and optional graph publication. Its documented schema carries source files and locations but does not require a unique exact quote and span for every semantic relation. Forge should borrow its confidence taxonomy, export ideas, and analysis patterns, and use it as a prototype comparator, not a production dependency or evidence authority.

LlamaIndex PropertyGraphIndex is the only external graph framework worth a bounded implementation comparison. It offers strict schema extraction, custom extractors, direct graph-store access, and an in-memory graph that can persist to disk ([LlamaIndex property graph guide](https://docs.llamaindex.ai/en/stable/module_guides/indexing/lpg_index_guide/)). The comparison must bypass its default LLM extraction, embedding retrievers, synonym retrieval, generated queries, and provider ownership: both candidates must receive the same already-verified claim ledger and produce the same bounded joins. Even then, adoption is warranted only if it reduces implementation or improves measured candidate recall without weakening provenance. **The default production decision remains a Forge-owned graph contract, initially backed by the smallest typed structure that supports required traversals.**

## Ownership boundaries preserve evidence and permit replacement

The target architecture should expose stable Forge domain interfaces around every replaceable component. This keeps framework choices reversible and prevents runtime conveniences from becoming product semantics.

| Layer | Forge-owned authority | Replaceable implementation | Prohibited responsibility |
|---|---|---|---|
| Ingestion and evidence | Normalized blocks, stable identities, offsets, exhaustive batch coverage, visual provenance, source hash | Format parsers and text splitters | Retrieval deciding which source text is eligible |
| Claim extraction | Claim schema, batch completeness, plan/run fingerprints, closed output shape | MCP sampling, agent fallback, optional dashboard model adapter | Model-assigned scores or unverified free-text findings |
| Verification and ledger | Unique source spans, quote re-location, occurrence/interpretation records, run reconciliation | Storage/serialization details | Treating chunk lineage or graph presence as verified evidence |
| Requirement graph | Node/edge vocabulary, graph bounds, generator versions, typed indexes | Plain Python adjacency, NetworkX, or a later proven adapter | Evidence eligibility, scoring, or truth by centrality/community |
| Consistency analysis | Candidate taxonomy, deterministic proofs, complete candidate plans, conservative consolidation | Parallel scheduler or optional LangGraph runtime | Open-ended agent search, omitted candidates, or model-authored severity |
| Findings | Publication rules, templates, consumers, consequences, required decisions, review order | Chat/dashboard rendering | Numeric risk claims or score effects before validation |
| Readiness scoring | Rubric, field constraints, verdicts, weights, gates, bands | None outside versioned Forge configuration | Graph metrics or deep-review classifiers changing the band |
| Workflow identity | `review_session_id`, ownership, `session_version`, `operation_id`, request digest, semantic events, expiry/deletion | Current SQLite repository; later coordinated checkpoint adapter | Vendor chat IDs, graph checkpoint IDs, or framework runs becoming authorization |
| Orchestration | Public `next_action`, legal transitions, inference budgets, side-effect policy | Current state machine or later LangGraph runtime | Framework topology becoming the public API |

The runtime flow should be: normalize the entire PRD; perform exhaustive claim-oriented extraction; verify every span; build the occurrence and interpretation ledger; derive reconciled typed claims without deleting alternatives; project the bounded graph; generate all candidates under versioned blocking rules; decide mechanical conflicts in Python; submit only semantic candidates to repeated closed-set classification; reverify endpoints and consolidate conservatively; retain the full consistency ledger; render prioritized advisory findings from templates; then display the unchanged deterministic readiness audit and enter the existing one-question remediation workflow. The deep-review graph and the workflow graph are different objects: the former represents PRD semantics, while the latter, if LangGraph is later adopted, coordinates execution.

**Phase 0 should freeze the contracts and evaluation target.** Define versioned claim, interpretation, graph, candidate, consistency-ledger, and finding schemas; add quote-local offset verification; define conservative relation and ambiguity taxonomies; and annotate the known MicroDrama defects plus hard negatives at the source-span and candidate levels. The golden set must include cross-batch conflicts, repeated identical quotes, scoped exceptions, legitimate alternatives, explicit supersession, unsupported units, and prompt injection. This phase should also record graph size, candidate counts, and expected output invariants rather than guessing infrastructure needs.

**Phase 1 should implement the smallest complete vertical slice without a framework migration.** Preserve all claims before current consolidation, build a typed in-memory graph, add deterministic candidate generators and proofs, add exhaustive fingerprinted classification plans, and produce a full consistency ledger plus template-rendered findings. The existing score path and SQLite workflow should remain unchanged. This isolates whether the product representation works before introducing an orchestration or graph abstraction that could obscure failures.

**Phase 2 should validate deep-review quality and operational behavior.** Measure claim-span recall, quote correctness, candidate recall, candidates per claim, classifier precision and recall by type, abstention, three-run agreement, finding precision and recall, duplicate rate, false-positive findings per PRD, missed implementation blockers, review-order agreement, decision actionability, latency, and token use. Evaluation should separate deterministic from semantic findings and preserve reviewer disagreement. Controlled transformations should test invariance to section order and batch boundaries and sensitivity to negation, numeric changes, scope exceptions, and supersession. CheckList and HANS both support capability-focused behavioral testing rather than trusting one aggregate NLP score ([CheckList](https://aclanthology.org/2020.acl-main.442/); [HANS](https://aclanthology.org/P19-1334/)).

**Phase 3 should run two bounded infrastructure comparisons.** First, compare plain typed adjacency with NetworkX and a stripped-down LlamaIndex PropertyGraphIndex using identical verified inputs, measuring code size, cold start, dependency surface, graph-build latency, candidate recall, duplicate rate, and export/debug value. Graphify can run as a non-authoritative reference on the same document to identify useful analysis patterns, not to establish truth. Second, implement one LangGraph vertical slice from verified claims through candidate classification, human interrupt, answer delta, and rescore. Set `thread_id` exactly to `review_session_id`, retain the Forge repository as authority, disable time travel, isolate side effects, and run existing restart, concurrency, stale-version, duplicate-operation, request-digest, wrong-document, cross-client resume, expiry, deletion, and no-overwrite tests unchanged.

**Phase 4 should adopt only what passes explicit value gates.** LangGraph should enter production only if the spike demonstrates substantial net deletion after adapter, migration, checkpoint, compatibility, and failure-handling code are counted; crash injection must show no duplicate model calls, answers, events, files, or fabricated run agreement. Persistence replacement, if ever useful, should follow as a separate migration with one atomic authority and a workflow-schema compatibility policy. NetworkX or LlamaIndex should be adopted only if they outperform the simpler structure on representative PRDs without changing the domain contract. GraphRAG, a graph database, embeddings, or cross-review memory should be reconsidered only after Forge acquires a concrete multi-document retrieval requirement, graph sizes that exceed in-process operation, concurrent graph-query workloads, or validated evidence that deterministic blocking misses important conflicts that semantic expansion can recover.

## Conclusion

The deep-review pivot changes Forge's center of gravity from field completeness to **source-bound relationship analysis**, but it does not require turning Forge into an agent platform or knowledge-retrieval system. The durable asset is the versioned claim and consistency representation: once every finding can be traced from a rendered decision back through a classified candidate to uniquely located source spans, orchestration and graph libraries become interchangeable implementation details rather than trust dependencies.

The important adoption threshold is therefore not document length. It is the emergence of requirements the minimal design cannot meet. LangGraph becomes justified when durable parallel work and human branching exceed the current state machine; a graph framework becomes justified when measured traversal or storage needs exceed typed in-process joins; GraphRAG becomes justified only when the product problem becomes corpus retrieval and synthesis. Until those thresholds are crossed, Forge should spend complexity on claim recall, contradiction precision, conservative publication, and human validation, because those determine whether deep review is correct and useful.
