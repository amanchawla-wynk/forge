# LangGraph and LangChain for Forge's Deep-Review Workflow

Research snapshot: 25 September 2026. This assessment uses the current LangGraph 1.x and LangChain v1 documentation and repository releases available on that date. LangGraph's release page listed `langgraph==1.2.12` on 21 September 2026; the package and its checkpoint libraries are independently versioned. [Source](https://github.com/langchain-ai/langgraph/releases)

## Which exact current framework primitives map to Forge?

### Takeaway

LangGraph has direct primitives for Forge's control flow, resumable pauses, checkpoint snapshots, retries, and execution history. LangChain has useful model-facing conveniences for structured output and model/tool retries, but those conveniences assume a model adapter that Forge deliberately does not own in its MCP/core path. Neither framework replaces Forge's domain state, evidence ledger, identity and authorization envelope, exact-source verification, deterministic consolidation, or scoring.

### Cited Findings

#### Forge baseline

- Forge currently separates the client's model from its trusted Python core: the model extracts facts and quotes, while Python validates evidence and deterministically computes verdicts, gates, weights, and bands. The MCP path does not own provider credentials or direct provider calls. [Source](https://github.com/amanchawla-wynk/forge/blob/main/docs/ARCHITECTURE.md#boundary); [Source](https://github.com/amanchawla-wynk/forge/blob/main/docs/DECISIONS.md#d-005-extraction-evidence-then-deterministic-scoring); [Source](https://github.com/amanchawla-wynk/forge/blob/main/docs/DECISIONS.md#d-006-client-llm-only)
- Forge's durable workflow state includes an immutable source/rubric-bound baseline extraction, assessment, framing, question queue, verified and pending answers, edge-case coverage, and checkpoint accounting. Ordinary answers advance a deterministic queue without model work; a bounded checkpoint extracts only answer deltas and affected criteria. [Source](https://github.com/amanchawla-wynk/forge/blob/main/docs/ARCHITECTURE.md#mcp-tool-direction); [Source](https://github.com/amanchawla-wynk/forge/blob/main/docs/DECISIONS.md#d-040-checkpoint-remediation-and-extract-only-answer-deltas)
- Forge persists sessions in SQLite under an opaque `review_session_id`, binds them to source hash, rubric version, workspace, and local user, and requires `session_version` plus `operation_id` for every mutation. Its repository atomically updates session state, an operation record, and an event record. [Source](https://github.com/amanchawla-wynk/forge/blob/main/docs/DECISIONS.md#d-042-forge-owns-review-identity-and-new-chats-resume-explicit); [Source](https://github.com/amanchawla-wynk/forge/blob/main/src/forge/sessions.py)
- Forge additionally binds an idempotency key to operation type and a digest of the request, reserves long-running external work before inference, rejects concurrent pending work, and returns a cached completed result on a safe retry. [Source](https://github.com/amanchawla-wynk/forge/blob/main/docs/DECISIONS.md#d-043-harden-durable-review-integrity-before-expanding-scope); [Source](https://github.com/amanchawla-wynk/forge/blob/main/src/forge/sessions.py)

#### What the frameworks do not remove

- They do not remove document normalization, stable source-block identity, exhaustive batching, source offsets, visual provenance, or plan/delta fingerprints. These are Forge's evidence eligibility and freshness guarantees. [Source](https://github.com/amanchawla-wynk/forge/blob/main/docs/ARCHITECTURE.md#dependency-strategy)
- They do not remove the multi-claim ledger or bounded requirement graph planned for deep review. LangGraph is a workflow graph, not Forge's domain graph of claims, requirements, actors, states, metrics, precedence, and source locations. [Source](https://github.com/amanchawla-wynk/forge/blob/main/docs/ARCHITECTURE.md#components); [Source](https://github.com/amanchawla-wynk/forge/blob/main/docs/DECISIONS.md#d-045-make-evidence-backed-deep-review-the-primary-experience)
- They do not remove schema-exact extraction validation, exact quote verification, criterion-local supplemental evidence, edge-case ledger verification, modal/pessimistic consolidation, deterministic question ordering, report derivation, or scoring. [Source](https://github.com/amanchawla-wynk/forge/blob/main/docs/SCORING_THEORY.md)
- They do not remove Forge's transport boundary. Native MCP sampling and the prepare/submit fallback let the connected client perform inference without a provider key in Forge; LangChain's documented model and agent examples instantiate provider/model integrations instead. [Source](https://github.com/amanchawla-wynk/forge/blob/main/docs/ARCHITECTURE.md#inference-modes); [Source](https://docs.langchain.com/oss/python/langchain/structured-output)

### Inferences

- LangGraph could remove meaningful orchestration code only if Forge lets it own the sequence of initial extraction, claim retention, consistency classification, human questions, delta checkpoints, revision approval, and final assessment. Using only `StateGraph` routing while retaining the current repository and manual pause protocol would improve visualization but remove little code.
- The best conceptual mapping is `review_session_id -> thread_id`, `RemediationState -> graph state`, each externally visible `next_action -> interrupt or next node`, and each expensive/side-effecting inference boundary -> a separately reserved, idempotent node. `session_version`, `operation_id`, ownership bindings, semantic events, and deterministic scoring remain an outer Forge envelope.
- LangChain's strongest value is confined to an adapter that already owns a direct model invocation, principally the optional dashboard. It has little leverage over MCP sampling and no leverage over agent-driven fallback JSON because the model call occurs outside the Forge process.
- LangGraph's long-term `Store` is unnecessary and potentially harmful for current Forge semantics. Review-local checkpointed state is enough; cross-thread memory risks contaminating evidence unless it is explicitly non-evidence context.

### Gaps

- The official LangGraph documentation reviewed here does not identify a built-in compare-and-swap equivalent to Forge's externally supplied `session_version`, nor a request-payload-bound idempotency ledger equivalent to `(review_session_id, operation_id, operation_type, request_digest)`. A spike must verify this against the exact checkpointer API and concurrency tests rather than assuming checkpoint versions provide the same contract. [Source](https://docs.langchain.com/oss/python/langgraph/checkpointers#checkpointer-interface)
- The docs describe SQLite checkpointing as ideal for experimentation/local workflows but do not establish its behavior under Forge's exact multi-client concurrency, TTL, deletion, permissions, WAL, and atomic event/operation requirements. [Source](https://docs.langchain.com/oss/python/langgraph/checkpointers#checkpointer-libraries)
- No official first-party primitive was found that turns MCP server-to-client sampling into a LangChain `BaseChatModel` without introducing a custom adapter. Suitability for borrowed inference therefore needs a small implementation experiment, especially after the MCP sampling deprecation noted by Forge. [Source](https://github.com/amanchawla-wynk/forge/blob/main/docs/DECISIONS.md#d-039-check-the-sampling-capability-before-sending-a-request)

## What migration and replay/idempotency hazards exist?

### Takeaway

The principal hazard is mistaking durable execution for exactly-once domain behavior. LangGraph intentionally re-executes nodes during interrupt resume, replay, and failure recovery; Forge's inference calls, answer recording, revision writes, and event updates therefore still need operation reservation, deterministic node boundaries, and domain idempotency. A second hazard is replacing Forge's linear optimistic-concurrency model with checkpoint branches without defining which branch is authoritative.

### Cited Findings

#### Replay and interrupt behavior

- Resuming an interrupt restarts the entire node from its beginning, so code before `interrupt()` executes again. LangGraph explicitly requires side effects before interrupts to be idempotent or moved into separate nodes. [Source](https://docs.langchain.com/oss/python/langgraph/interrupts#rules-of-interrupts)
- Multiple interrupts within a node are matched by index. Reordering, conditionally skipping, or non-deterministically looping over interrupts can pair resumed answers with the wrong interruption. [Source](https://docs.langchain.com/oss/python/langgraph/interrupts#do-not-reorder-interrupt-calls-within-a-node)
- Time-travel replay does not read cached outputs after the chosen checkpoint: downstream nodes, LLM calls, API requests, and interrupts execute again and may produce different results. [Source](https://docs.langchain.com/oss/python/langgraph/use-time-travel#replay)
- `update_state` does not roll a thread back. It creates a new checkpoint branch while preserving the original history. [Source](https://docs.langchain.com/oss/python/langgraph/use-time-travel#fork)
- Checkpoints exist at super-step boundaries, while successful node writes within a partially failed super-step may be retained as pending writes and skipped on resume. [Source](https://docs.langchain.com/oss/python/langgraph/checkpointers#super-steps); [Source](https://docs.langchain.com/oss/python/langgraph/checkpointers#pending-writes)
- LangGraph offers `exit`, `async`, and `sync` durability. `async` has a small crash window; `exit` cannot recover from a process crash mid-execution; `sync` persists before the next step at a performance cost. [Source](https://docs.langchain.com/oss/python/langgraph/checkpointers#durability-modes)

#### Concrete Forge hazards and required mitigations

| Hazard | Failure in Forge terms | Required mitigation |
|---|---|---|
| Duplicate borrowed inference after resume/replay | A checkpoint extraction may be requested twice, incur duplicate cost, or be misrepresented as independent model agreement. Replay explicitly re-runs LLM calls. [Source](https://docs.langchain.com/oss/python/langgraph/use-time-travel#replay) | Keep Forge's pre-inference operation reservation and request digest. Persist the returned extraction under that operation before graph advancement. Do not assign a fresh `run_index` merely because a runtime retry occurred. [Source](https://github.com/amanchawla-wynk/forge/blob/main/docs/DECISIONS.md#d-043-harden-durable-review-integrity-before-expanding-scope) |
| Duplicate answer/event mutation | An interrupted answer node could append the same answer or semantic event twice when restarted. Interrupt nodes restart from the beginning. [Source](https://docs.langchain.com/oss/python/langgraph/interrupts#rules-of-interrupts) | Put `interrupt()` before mutation, then commit the answer once through the existing `(operation_id, request_digest)` ledger. Prefer one interrupt per node and one answer mutation in its successor. |
| Duplicate revision file write | Replay could try to recreate an output or overwrite a path after the first execution succeeded but before its checkpoint committed. [Source](https://docs.langchain.com/oss/python/langgraph/use-time-travel#replay) | Preserve Forge's refusal to overwrite, approved plan digest, reserved operation, and artifact provenance. Treat “file exists with matching digest” as an idempotent recovery case only after explicit verification. [Source](https://github.com/amanchawla-wynk/forge/blob/main/docs/DECISIONS.md#d-041-preview-integrated-revisions-and-verify-a-new-copy) |
| Lost-update/concurrent-chat race | Two chats invoking the same `thread_id` could both act on the same visible state unless the runtime/checkpointer provides the same compare-and-swap behavior as `session_version`. | Retain `session_version` as an API precondition and serialize/reserve mutations in Forge's repository. Do not expose LangGraph checkpoint ids as a substitute until a concurrency spike proves stale writes are rejected. [Source](https://github.com/amanchawla-wynk/forge/blob/main/src/forge/sessions.py) |
| Silent branch divergence | `update_state` creates a fork rather than replacing history, so two valid descendants may exist for one review. [Source](https://docs.langchain.com/oss/python/langgraph/use-time-travel#fork) | Disable user-facing time travel initially, or record an explicit authoritative branch/head in the Forge session envelope and increment `session_version` when it changes. Starting a new review should still allocate a new Forge id rather than an implicit checkpoint fork. |
| State reducer corruption | Reducers accumulate rather than overwrite; concurrent branches may merge lists or claims in an order that changes results. `update_state` also applies reducers. [Source](https://docs.langchain.com/oss/python/langgraph/checkpointers#update-state) | Use replace semantics for immutable verified snapshots; use reducers only for append-only, identity-keyed candidate collections; run Forge validation after every merge. Never let a reducer consolidate claims or assign score credit. |
| Dynamic question/interrupt mismatch | Queue changes after checkpointing could reorder interrupt calls and bind an answer to the wrong field. Interrupt resume matching is index-based within a task. [Source](https://docs.langchain.com/oss/python/langgraph/interrupts#do-not-reorder-interrupt-calls-within-a-node) | One question per interrupt node, with stable criterion/field/cell identity in the payload. Rebuild the queue only in a subsequent deterministic node after verified scoring, as Forge already does. [Source](https://github.com/amanchawla-wynk/forge/blob/main/docs/SCORING_THEORY.md#remediation) |
| Graph-code/schema upgrade against old checkpoints | Persisted checkpoints contain state and node-position assumptions; changing node names, routes, reducers, or interrupt order can make old reviews unsafe to resume. The checkpointer contract stores graph-native serialized state and metadata. [Source](https://docs.langchain.com/oss/python/langgraph/checkpointers#serializer) | Add a Forge workflow-schema version and explicit migration/compatibility policy. Pin framework/checkpointer versions. Test old-session resume across releases. Reject rather than guess when a graph version is incompatible. |
| Dual source of truth | Keeping `review_sessions.state_json` and LangGraph checkpoints can let them disagree after a partial commit. | During a spike, designate the Forge session envelope as authoritative and treat graph checkpoints as derived, or implement a custom checkpointer/transaction boundary that commits the graph head, operation result, semantic event, and `session_version` atomically. LangGraph documents a custom `BaseCheckpointSaver` contract and conformance suite, but Forge would own this integration. [Source](https://docs.langchain.com/oss/python/langgraph/checkpointers#build-a-custom-checkpointer) |
| Checkpoint growth and sensitive content | Full state is saved per super-step by default; long-running reviews can grow without bound and retain PRD text/answers in serialized snapshots. [Source](https://docs.langchain.com/oss/python/langgraph/checkpointers#optimize-checkpoint-storage) | Keep state minimal, avoid duplicating normalized PRD text in every state channel, preserve Forge TTL/deletion, test secure file permissions, and define redaction. `DeltaChannel` may reduce storage but is beta and adds ancestor-chain retention constraints. [Source](https://docs.langchain.com/oss/python/langgraph/checkpointers#delta-channel-support) |
| Observability data exfiltration | LangSmith traces are a hosted observability path requiring an account/API key and can contain prompts, model inputs, state, and tool activity. [Source](https://docs.langchain.com/langsmith/observability) | Do not enable LangSmith in the default MCP/core path. If later offered, make it opt-in, separately configured, redacted, and covered by a new architecture/security decision. Prefer local semantic events and local graph history initially. |

#### Migration shape

- A flag-day replacement of `ReviewSessionRepository` is unsafe because the current store provides product contracts beyond persistence: exact-document discovery, ownership binding, explicit cross-client resume, optimistic concurrency, operation reservation, result caching, expiry, and semantic events. [Source](https://github.com/amanchawla-wynk/forge/blob/main/src/forge/sessions.py)
- A safer spike is an adapter around one bounded workflow, using `thread_id=review_session_id` while retaining the current Forge envelope. Compare the graph checkpoint head with the current `session_version`, and run the existing restart, stale-version, duplicate-operation, wrong-document, explicit parallel-review, and cross-client resume tests unchanged. Those test classes are already part of Forge's recorded regression coverage. [Source](https://github.com/amanchawla-wynk/forge/blob/main/docs/ROADMAP.md#completed)
- Persisted sessions need a migration strategy before adoption: dual-read/dual-write is risky because it creates two authorities, while one-time conversion needs a stable mapping from each `WorkflowState` and `RemediationState` to a graph checkpoint and next node. Forge's roadmap already calls for a spike specifically covering checkpointing, interrupts, replay safety, and audit preservation. [Source](https://github.com/amanchawla-wynk/forge/blob/main/docs/ROADMAP.md#current-build)

### Inferences

- LangGraph's checkpoint id is not Forge's `session_version`. A checkpoint identifies a historical graph snapshot and can have descendants/forks; `session_version` is an externally visible monotonic compare-and-swap token for the one authoritative review head.
- LangGraph's run/task ids and LangChain tool-call ids are not Forge's `operation_id`. They identify executions, while Forge's idempotency key is caller-supplied, stable across network retries, scoped to a review, and bound to operation type plus request payload.
- “Exactly once” must remain an application-level illusion built from reservation, idempotent effects, and result caching. LangGraph provides at-least-once re-execution behavior around failure and resume, which is useful only when nodes respect that contract.
- The graph should keep expensive model work in small, isolated nodes and use `sync` durability around committed external effects. Pure deterministic transforms can safely be replayed and may use less expensive durability settings.
- Existing SQLite sessions can be migrated incrementally only if graph orchestration first proves value without replacing identity. Persistence replacement should be a second, independent decision after parity tests.

### Gaps

- Official docs reviewed do not specify an out-of-the-box transaction spanning LangGraph's checkpoint tables and arbitrary Forge operation/event/session tables. A custom saver or repository coordination experiment is required. [Source](https://docs.langchain.com/oss/python/langgraph/checkpointers#checkpointer-interface)
- Official docs reviewed do not establish how concurrent invocations against one SQLite `thread_id` are serialized or rejected in a way equivalent to Forge's `BEGIN IMMEDIATE` plus expected-version update. This must be stress-tested against the exact `langgraph-checkpoint-sqlite` version. [Source](https://docs.langchain.com/oss/python/langgraph/checkpointers#checkpointer-libraries)
- The cost of serializing Forge's large `RemediationState`, claim ledger, and future requirement graph at each super-step is unknown. Representative large PRDs are needed to measure database growth, resume latency, and pruning safety.

## Should Forge adopt LangGraph, LangChain, both, or neither, and at what stage?

### Takeaway

Recommendation: adopt neither in the production MCP/core path now. Run a narrow LangGraph-only spike during the current deep-review build, after the claim/finding schemas and deterministic candidate pipeline are stable enough to express as nodes. Adopt LangGraph later only if it demonstrably removes substantial orchestration/recovery code while all Forge identity, idempotency, evidence, and scoring contracts remain intact. Do not adopt LangChain as a core dependency; consider only a separately packaged dashboard/model-adapter experiment if structured-output negotiation measurably outperforms the existing LiteLLM/Pydantic path.

#### Staged recommendation

1. **Now: finish domain representation before framework migration.** Define the multi-claim evidence ledger, consistency ledger, finding schema, bounded requirement graph, deterministic candidate generation, and quote-verification rules first. These are the deep-review product and trust model and cannot be delegated to either framework. [Source](https://github.com/amanchawla-wynk/forge/blob/main/docs/ROADMAP.md#current-build)
2. **Current-build spike: LangGraph only, one bounded vertical slice.** Model the path `verified claim ledger -> candidate pairs -> closed-set classifications -> Python verification -> prioritized finding -> human interrupt -> answer delta -> deterministic rescore`. Use `thread_id=review_session_id`; keep Forge's current session/operation/event envelope authoritative; do not enable time travel to users; do not add provider integrations.
3. **Parity gate: run existing guarantees unchanged.** The spike must pass restart, stale-version, duplicate-operation, request-digest mismatch, concurrent pending operation, wrong-document, exact discovery, parallel review, cross-client resume, expiry/deletion, source/rubric change, stale plan, and revision no-overwrite tests. Forge records these behaviors as implemented requirements, not incidental code. [Source](https://github.com/amanchawla-wynk/forge/blob/main/docs/ROADMAP.md#completed)
4. **Value gate: measure code and operational reduction.** Adopt only if the spike materially reduces bespoke routing, pause/resume, retry, partial-failure, or progress-streaming code after counting the adapter, migration, custom checkpointer, and compatibility code it adds. D-040's threshold is “durable branching, background execution, or multi-party approvals”; the current roadmap uses the equivalent test of removing material orchestration code without weakening identity or idempotency. [Source](https://github.com/amanchawla-wynk/forge/blob/main/docs/DECISIONS.md#d-040-checkpoint-remediation-and-extract-only-answer-deltas); [Source](https://github.com/amanchawla-wynk/forge/blob/main/docs/ROADMAP.md#current-build)
5. **If adopted: use LangGraph as an internal runtime, not the product boundary.** Preserve Forge DTOs and MCP tools, map graph output to the existing `next_action`, keep Pydantic domain models and deterministic services callable without LangGraph, and retain Forge's semantic event log. This maintains the documented transport/model-provider independence of the domain workflow. [Source](https://github.com/amanchawla-wynk/forge/blob/main/docs/ARCHITECTURE.md#portability)
6. **Defer persistence replacement.** First adopt orchestration with the Forge envelope intact. Only after successful parity and load tests should Forge consider a custom `BaseCheckpointSaver` or consolidated SQLite schema that atomically preserves graph checkpoints and Forge operations/events. LangGraph supplies a checkpointer protocol and conformance suite, but a custom implementation remains Forge-owned code. [Source](https://docs.langchain.com/oss/python/langgraph/checkpointers#build-a-custom-checkpointer)
7. **Keep LangChain optional and adapter-scoped.** A later dashboard-only experiment may compare `ProviderStrategy`/`ToolStrategy`, validation retry behavior, and model metadata normalization with the current LiteLLM calls. It must remain in the optional dashboard dependency group and must not alter the evidence/scoring core. [Source](https://docs.langchain.com/oss/python/langchain/structured-output); [Source](https://github.com/amanchawla-wynk/forge/blob/main/docs/DECISIONS.md#d-033-optional-local-dashboard-with-bring-your-own-key-inference)
8. **Do not adopt LangSmith by default.** Local graph history and Forge semantic events are enough for the spike. LangSmith may be evaluated later as explicit opt-in telemetry because its normal setup requires a LangSmith account/API key and introduces data-governance questions. [Source](https://docs.langchain.com/langsmith/observability#get-started)

#### Spike acceptance criteria

- `thread_id` is exactly the Forge `review_session_id`; MCP transport/chat ids remain metadata only. [Source](https://github.com/amanchawla-wynk/forge/blob/main/docs/DECISIONS.md#d-042-forge-owns-review-identity-and-new-chats-resume-explicit)
- Every external mutation still requires the current `session_version` and a unique `operation_id` bound to operation type and request digest; stale and conflicting retries fail deterministically. [Source](https://github.com/amanchawla-wynk/forge/blob/main/src/forge/sessions.py)
- A crash at every node boundary can be resumed without duplicated model charges, answers, events, generated files, or fabricated extraction agreement.
- Replay is disabled or guarded for inference and artifact nodes; an explicit replay cannot silently alter the authoritative assessment.
- No model provider SDK, provider credential, or LangSmith key enters the default MCP/core dependency path. [Source](https://github.com/amanchawla-wynk/forge/blob/main/pyproject.toml); [Source](https://github.com/amanchawla-wynk/forge/blob/main/docs/DECISIONS.md#d-006-client-llm-only)
- Schema-valid but source-unsupported claims still receive no credit; graph state and reducers never bypass `locate_quote`, edge-ledger verification, extraction-plan fingerprints, or deterministic scoring. [Source](https://github.com/amanchawla-wynk/forge/blob/main/docs/SCORING_THEORY.md#evidence-rule)
- Existing domain services remain directly testable without running a graph, preserving Forge's framework independence.
- Measured net deletion is substantial enough to justify a new runtime and checkpoint dependency; otherwise retain the existing state machine.

### Inferences

- The likely winning architecture is **Forge domain core + Forge identity/idempotency envelope + optional LangGraph orchestration runtime**, not “Forge rewritten as a LangChain agent.”
- LangGraph becomes more compelling if deep review needs parallel classifier fan-out, partial-failure recovery, background execution, multiple approval roles, or long-running branchable investigations. It remains unnecessary if the implemented workflow stays a mostly linear sequence of deterministic services and one-user pauses.
- LangChain would add the most abstraction exactly where Forge has the least control: provider/model invocation. Its structured-output conveniences do not justify coupling the MCP/core path to model integrations, and its agent loop would weaken Forge's closed-set, deterministic control policy.
- The adoption decision should be made after a code-delta and failure-injection comparison, not from feature-list overlap. LangGraph can appear to replace persistence while forcing Forge to rebuild the harder product contracts around it.

### Gaps

- Representative deep-review orchestration code does not yet exist, so the amount of net code LangGraph would remove cannot be measured today. The planned claim/consistency pipeline must reach a vertical slice first. [Source](https://github.com/amanchawla-wynk/forge/blob/main/docs/ROADMAP.md#current-build)
- No benchmark yet compares the current SQLite repository with `SqliteSaver` for Forge-sized state, concurrent MCP/dashboard access, crash recovery, and database growth.
- No prototype yet proves MCP sampling or the agent-driven fallback can be represented as graph nodes/interrupts without making the workflow less clear to clients.
- The replacement for deprecated MCP sampling noted in Forge's decision log remains unresolved; adopting a model abstraction before SEP-2577 is understood could optimize the wrong boundary. [Source](https://github.com/amanchawla-wynk/forge/blob/main/docs/DECISIONS.md#d-039-check-the-sampling-capability-before-sending-a-request)
