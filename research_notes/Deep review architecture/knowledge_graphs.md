# Knowledge-Graph Options for Forge Deep Review

Research current as of 2026-09-25. Scope: deep review of one 20-100 page PRD, specifically linking source-backed requirements and surfacing cross-section contradiction candidates. This is not an evaluation of general-purpose RAG or long-term agent memory.

## Is one PRD enough data to justify each system?

### Takeaway

One PRD is enough input for every option to build *a* graph, but it does not justify the architecture of most options. A small Forge-owned property graph is the best production fit; LlamaIndex PropertyGraphIndex is the only external framework worth a bounded comparison spike, while Graphify is useful as a design reference and prototype comparator. Microsoft GraphRAG, Graphiti, and Cognee optimize for corpus retrieval, evolving memory, or repeated reuse that a single static PRD does not provide. [Forge architecture](../../docs/ARCHITECTURE.md#components); [GraphRAG overview](https://microsoft.github.io/graphrag/); [Graphiti overview](https://help.getzep.com/graphiti/graphiti/overview); [Cognee architecture](https://docs.cognee.ai/core-concepts/architecture)

#### Microsoft GraphRAG

- GraphRAG says it improves reasoning over “large data collections or even singular large documents,” so a 20-100 page PRD is not too small to run technically. [GraphRAG overview](https://microsoft.github.io/graphrag/)
- Its index creates text units, extracts entities/relationships/claims, performs hierarchical Leiden clustering, and generates bottom-up community summaries. Its query layer then offers global, local, DRIFT, and basic top-*k* search. [GraphRAG overview](https://microsoft.github.io/graphrag/)
- Standard indexing uses an LLM for entity extraction, relationship extraction, entity summarization, relationship summarization, optional claim extraction, and community-report generation. Microsoft estimates graph extraction at “roughly 75% of indexing cost.” [GraphRAG indexing methods](https://microsoft.github.io/graphrag/index/methods/)
- FastGraphRAG reduces cost with noun-phrase extraction and co-occurrence edges, but Microsoft says its graph is “quite a bit noisier” and is primarily aimed at summary questions using global search. [GraphRAG indexing methods](https://microsoft.github.io/graphrag/index/methods/)

#### LlamaIndex PropertyGraphIndex

- PropertyGraphIndex provides orchestration for “constructing a graph” and “querying a graph.” Construction applies `kg_extractors` to each chunk and stores entities and relations in each LlamaIndex node's metadata. [LlamaIndex property-graph guide](https://docs.llamaindex.ai/en/stable/module_guides/indexing/lpg_index_guide/)
- The default extractors are `SimpleLLMPathExtractor` and `ImplicitPathExtractor`; the former asks an LLM for single-hop triples, while the latter only reads relationships already present on nodes and needs no LLM or embedding model. [LlamaIndex property-graph guide](https://docs.llamaindex.ai/en/stable/module_guides/indexing/lpg_index_guide/)
- `SchemaLLMPathExtractor` can use Pydantic structured output and a strict entity/relation schema, and custom extractors can be implemented by subclassing `TransformComponent`. [LlamaIndex property-graph guide](https://docs.llamaindex.ai/en/stable/module_guides/indexing/lpg_index_guide/)
- The default `SimplePropertyGraphStore` is in-memory and persists to disk; server integrations include Neo4j, Nebula, TiDB, and FalkorDB. [LlamaIndex property-graph guide, Storage](https://docs.llamaindex.ai/en/stable/module_guides/indexing/lpg_index_guide/#storage)

#### Graphiti

- Graphiti models entities, temporal facts, and episodes. Its repository says every derived fact traces back to an episode, facts have validity windows, and new data integrates without full graph recomputation. [Graphiti repository](https://github.com/getzep/graphiti)
- Its stated use cases are agents that learn from interactions and systems with changing CRM, billing, customer-service, health, or finance state. [Graphiti overview](https://help.getzep.com/graphiti/graphiti/overview)
- Graphiti explicitly contrasts itself with GraphRAG by calling GraphRAG static/batch oriented and Graphiti continuous, incremental, and bi-temporal. [Graphiti overview](https://help.getzep.com/graphiti/graphiti/overview)

#### Cognee

- Cognee describes itself as persistent long-term memory across sessions that turns “documents, code, and conversations” into a self-hosted knowledge graph. Its operations are `remember`, `recall`, `improve`, and `forget`. [Cognee repository](https://github.com/topoteretes/cognee)
- Cognee's architecture says “No single database can handle all aspects of memory” and therefore combines relational, vector, and graph stores. [Cognee architecture](https://docs.cognee.ai/core-concepts/architecture)
- Its local quickstart still extracts a graph and embeds text; LLM-dependent improvement stages can be skipped, but embeddings and retrieval remain part of the model. [Cognee repository](https://github.com/topoteretes/cognee)

#### Graphify

- Graphify maps projects containing code, docs, PDFs, images, and video into a persistent graph and emits `graph.html`, `GRAPH_REPORT.md`, and `graph.json`. [Graphify repository](https://github.com/Graphify-Labs/graphify)
- Its pipeline is `detect -> extract -> build -> cluster -> analyze -> report -> export`; stages exchange Python dictionaries and NetworkX graphs. [Graphify architecture](https://github.com/Graphify-Labs/graphify/blob/v8/ARCHITECTURE.md)
- Graphify is explicitly “not a vector index”; it uses graph traversal and community detection rather than embeddings/vector storage. [Graphify repository](https://github.com/Graphify-Labs/graphify)

#### Forge-owned bounded graph

- NetworkX allows arbitrary node and edge attributes, directed edges, and parallel edges. Parallel edges are important when two claims connect the same requirement/actor but have different source spans, phases, modalities, or extraction runs. [NetworkX `MultiDiGraph`](https://networkx.org/documentation/stable/reference/classes/multidigraph.html)
- Forge already requires a “bounded graph” linking requirements, actors, metrics, dependencies, states, rollout rules, and sections, with source spans verified before findings are shown. [Forge architecture](../../docs/ARCHITECTURE.md#components)
- Forge's accepted D-045 decision requires comparison against “a smaller Forge-owned static graph” and forbids the graph from choosing evidence eligibility or assigning numeric scores. [Forge decisions, D-045](../../docs/DECISIONS.md#d-045-make-evidence-backed-deep-review-the-primary-experience)

### Inferences

- **Recommended production baseline:** Build the graph directly from Forge's exhaustive, verified claim ledger. For a single PRD, expected graph size is bounded by source blocks and extracted requirement atoms, so an in-process adjacency structure is operationally sufficient. This follows Forge's existing per-document boundary and NetworkX's support for attributed multiedges. [Forge architecture](../../docs/ARCHITECTURE.md#components); [NetworkX `MultiDiGraph`](https://networkx.org/documentation/stable/reference/classes/multidigraph.html)
- **Recommended comparator:** Spike LlamaIndex only against the exact bounded use case: same verified input claims, no vector retriever, no generated Cypher, no external graph server, and no direct provider calls. Its custom extractor/direct graph-store APIs make this possible, but most of its default extraction and retrieval behavior should be bypassed. [LlamaIndex property-graph guide](https://docs.llamaindex.ai/en/stable/module_guides/indexing/lpg_index_guide/)
- **Graphify role:** Borrow its confidence taxonomy, JSON export ideas, and graph-analysis patterns; do not assume its semantic extractor or source-location fields satisfy Forge's exact-quote evidence contract. [Graphify architecture](https://github.com/Graphify-Labs/graphify/blob/v8/ARCHITECTURE.md)
- **Reject for this scope:** GraphRAG's communities/summaries, Graphiti's temporal invalidation, and Cognee's persistent multi-store memory do not answer a requirement-pairing need that an attributed per-document graph cannot answer. [GraphRAG overview](https://microsoft.github.io/graphrag/); [Graphiti overview](https://help.getzep.com/graphiti/graphiti/overview); [Cognee architecture](https://docs.cognee.ai/core-concepts/architecture)

### Gaps

- No primary source provides a benchmark for contradiction precision/recall on one 20-100 page PRD for any of these systems.
- No reviewed external system documents Forge-equivalent guarantees that every normalized source block participates in extraction and that retrieval can never determine absence.
- A measured Forge spike is still needed to compare implementation effort, candidate recall, duplicate rate, token use, and latency between a plain Forge structure, NetworkX, and a stripped-down LlamaIndex graph. Forge's roadmap already requires this comparison. [Forge roadmap](../../docs/ROADMAP.md#current-build)

## What provenance, exact quote, local-first, and provider-independent capabilities exist?

### Takeaway

Several systems retain source chunks or episodes, but none documents Forge's complete contract: exact source quote, stable source location, complete-document eligibility, and mechanical quote verification before display. Local deployment is widely possible, but provider independence is weaker where the framework itself owns LLM/embedding calls. The Forge-owned graph is the only option that preserves the existing MCP-client inference boundary by construction. [Forge scoring theory](../../docs/SCORING_THEORY.md#evidence-rule); [Forge architecture](../../docs/ARCHITECTURE.md#inference-modes)

### Inferences

- “Has provenance” must not be treated as equivalent to “Forge-eligible evidence.” Chunk IDs, episode links, or source filenames narrow the audit trail, but only an exact quote mechanically located in Forge's normalized corpus should support a surfaced finding. [Forge scoring theory](../../docs/SCORING_THEORY.md#evidence-rule)
- The graph should be a projection of the verified claim ledger, not a second extraction corpus. This avoids two competing provenance systems and prevents graph normalization, entity summaries, or deduplication from replacing the original wording. [Forge architecture](../../docs/ARCHITECTURE.md#components)
- A contradiction finding should cite at least two independently verified source spans. The edge connecting them may be inferred/advisory, but both endpoint claims must be exact-source facts. This follows D-045's requirement that every finding cite verified locations. [Forge decisions, D-045](../../docs/DECISIONS.md#d-045-make-evidence-backed-deep-review-the-primary-experience)
- Provider independence means more than supporting several API vendors. For Forge core it means the graph package must not authenticate to or directly invoke any provider; model work remains with the connected MCP client or explicit agent-driven fallback. [Forge architecture](../../docs/ARCHITECTURE.md#boundary)

### Gaps

- External documentation generally describes lineage at chunk/episode granularity; it does not publish quote-verification false-positive/false-negative measurements.
- Graphify's public docs do not establish whether every semantic document edge always receives a non-null source location, and its published schema does not require a verbatim quote.
- LlamaIndex can preserve arbitrary metadata, but the reviewed docs do not promise stable source offsets through all parsers and graph stores.

### Inferences

- Embeddings do not solve Forge's central relation problem. Contradiction candidates should primarily come from shared structured keys such as subject, actor, object, state, metric, scope, phase, modality, numeric range, time window, or precedence target. Semantic similarity may be a later advisory recall aid, never an absence test. [Forge architecture](../../docs/ARCHITECTURE.md#components); [Forge scoring theory](../../docs/SCORING_THEORY.md#evidence-rule)
- Community detection is ill-matched to a deliberately typed graph built from one PRD. Sections and requirement domains already provide explicit grouping, while a learned community boundary can split related claims or imply significance without source authority. GraphRAG uses communities for holistic corpus summarization, a different objective. [GraphRAG overview](https://microsoft.github.io/graphrag/)
- A dedicated graph database is unnecessary until representative workloads demonstrate a need for graph persistence independent of assessment state, concurrent queries, Cypher, or graph sizes that exceed an in-process structure. None of those needs is established for one PRD. [Forge architecture](../../docs/ARCHITECTURE.md#components)
- Start with a Forge-owned typed adjacency model if required traversals are only one- or two-hop joins; adopt NetworkX if parallel edges, subgraph views, traversal algorithms, or export tooling measurably reduce code. NetworkX itself should remain replaceable behind Forge domain types. [NetworkX `MultiDiGraph`](https://networkx.org/documentation/stable/reference/classes/multidigraph.html)

### Gaps

- Representative PRD graph sizes are not yet measured. Record node/edge counts and candidate-pair counts during the golden-case spike before deciding whether NetworkX is worth a runtime dependency.
- Dependency size, cold-start impact, and transitive vulnerability surface were not benchmarked for LlamaIndex, Graphify, Graphiti, Cognee, or GraphRAG in the Forge package.
- Community detection might become useful for multi-document portfolio analysis, but that is outside the assigned one-PRD scope and outside Forge's present product definition.

## What should remain advisory versus scoring authority?

### Takeaway

The graph, all inferred links, contradiction classification, priority, consequence text, and suggested author decisions should remain advisory. Scoring authority must remain exactly where it is: exhaustive source eligibility, quote verification, rubric field validation, deterministic verdicts/weights/gates, and Python-selected bands. A graph finding may become authoritative only after a future versioned rubric defines its fields and evidence rules and representative human validation supports the change. [Forge architecture](../../docs/ARCHITECTURE.md#components); [Forge scoring theory](../../docs/SCORING_THEORY.md#validation-plan); [Forge decisions, D-045](../../docs/DECISIONS.md#d-045-make-evidence-backed-deep-review-the-primary-experience)

### Cited Findings

- Forge measures operational readiness, not prose quality or strategic correctness. The model extracts fields and verbatim evidence; Python derives verdicts and performs aggregation. [Forge scoring theory](../../docs/SCORING_THEORY.md#claim-being-measured); [Forge scoring theory](../../docs/SCORING_THEORY.md#extraction-before-judgment)
- The highest band requires every applicable criterion to be present; only rubric configuration controls weights and gates. [Forge scoring theory](../../docs/SCORING_THEORY.md#aggregation)
- Forge states that structured gaps and risks remain advisory and that the readiness band is not a Go/No-Go decision. [Forge scoring theory](../../docs/SCORING_THEORY.md#output-restraint)
- Forge's deep-review architecture says the graph is “not a retrieval eligibility filter or scoring authority,” exhaustive batching remains the evidence basis, and only versioned rubric rules can affect points or bands. [Forge architecture](../../docs/ARCHITECTURE.md#components)
- D-045 requires deep-review findings to remain outside the readiness band until representative human review establishes precision, recall, priority usefulness, and an acceptable false-positive rate. [Forge decisions, D-045](../../docs/DECISIONS.md#d-045-make-evidence-backed-deep-review-the-primary-experience)
- Forge's validation plan requires sensitivity tests, adversarial tests, model/human agreement, false-ready rates, and internal human labels before calibration claims. [Forge scoring theory](../../docs/SCORING_THEORY.md#validation-plan)

#### Proposed authority split

| Capability | Authority status | Required guardrail |
|---|---|---|
| Exhaustive source-block coverage | Scoring authority | Every normalized block appears in at least one extraction batch; incomplete batch sets are rejected. [Forge scoring theory](../../docs/SCORING_THEORY.md#evidence-rule); [Forge architecture](../../docs/ARCHITECTURE.md#dependency-strategy) |
| Exact quote and location validation | Scoring and display authority | Python must locate every cited quote in the normalized source before credit or display. [Forge scoring theory](../../docs/SCORING_THEORY.md#evidence-rule) |
| Claim normalization into actor, subject, scope, phase, modality, state, metric, range, timeline, or precedence properties | Advisory analysis input | Preserve the original verified quote and never let normalized values replace source text. [Forge architecture](../../docs/ARCHITECTURE.md#components) |
| Deterministic candidate pairing | Advisory | Generate candidates from all eligible verified claims, not top-*k* retrieval; retain the rule/reason that formed each pair. [Forge architecture](../../docs/ARCHITECTURE.md#components) |
| Model classification of “contradiction,” “possible conflict,” “compatible,” or “unclear” | Advisory | Closed output set; model sees both verified quotes and structured context; Python rejects unbound quotes and malformed choices. #### Recommended bounded graph contract

- **Nodes:** source block/section, verified claim, requirement atom, actor, object/entity, state, metric, event, dependency, rollout phase, platform, and defined term. This follows the entities already named by Forge's target architecture. [Forge architecture](../../docs/ARCHITECTURE.md#components)
- **Claim properties:** immutable claim ID; exact quote; source block ID; source start/end offsets; page/heading/paragraph location when reliable; extraction run IDs; criterion/field origin; modality (`must`, `should`, `may`, descriptive); polarity; scope; phase; value/range/unit; and provenance kind. D-045 and the roadmap already require exact quote provenance, scope, phase, modality, and run-aware claim retention. [Forge decisions, D-045](../../docs/DECISIONS.md#d-045-make-evidence-backed-deep-review-the-primary-experience); [Forge roadmap](../../docs/ROADMAP.md#current-build)
- **Edges:** `located_in`, `applies_to`, `requires`, `depends_on`, `defines`, `measures`, `transitions_to`, `precedes`, `supersedes`, `same_subject_candidate`, and `conflict_candidate`. Every inferred edge records generator version, rule/model identity, confidence class, and endpoint claim IDs; it is never promoted to source fact merely because it exists in the graph. This applies Forge's existing separation between verified evidence and advisory interpretation. [Forge architecture](../../docs/ARCHITECTURE.md#trust-boundaries)
- **Candidate generation:** exhaustively pair claims within deterministic blocking keys, then run cheap rule checks for unequal exact values, impossible/disjoint ranges, overlapping scope with opposing polarity, inconsistent timelines, competing precedence, undefined fallback, and stale/superseded text. Forge's roadmap names these candidate classes explicitly. [Forge roadmap](../../docs/ROADMAP.md#current-build)
- **Finding output:** require two or more verified quotes, source locations, finding type, advisory status, why the claims may conflict, affected consumers, implementation consequence, and the decision the author must make. D-045 requires verified locations, consequence, and required decision. [Forge decisions, D-045](../../docs/DECISIONS.md#d-045-make-evidence-backed-deep-review-the-primary-experience)

### Inferences

- A graph edge should never receive the same epistemic status as its endpoint claims. The claims may be source-verified while `conflict_candidate` is a deterministic or model-derived interpretation. [Forge architecture](../../docs/ARCHITECTURE.md#trust-boundaries)
- “No contradiction found” must not imply the PRD is contradiction-free. Forge can claim only that no candidate survived the declared extraction, pairing, and classification version; exhaustive source eligibility does not make semantic contradiction detection complete. [Forge scoring theory](../../docs/SCORING_THEORY.md#evidence-rule); [Forge decisions, D-045](../../docs/DECISIONS.md#d-045-make-evidence-backed-deep-review-the-primary-experience)
- Contradiction findings should initially be omitted rather than shown when either quote cannot be re-verified, scopes cannot be aligned, or model runs disagree without a pessimistic closed-set resolution. This minimizes false accusations while the feature is advisory. [Forge scoring theory](../../docs/SCORING_THEORY.md#repeated-extraction-and-confidence); [Forge decisions, D-045](../../docs/DECISIONS.md#d-045-make-evidence-backed-deep-review-the-primary-experience)
- A future scoring change requires a new rubric criterion with explicit required fields, objective constraints where possible, versioning, regression fixtures, and human-labelled validation. It must not arise by assigning weights to graph metrics such as centrality, community rank, edge confidence, or contradiction count. [Forge scoring theory](../../docs/SCORING_THEORY.md#validation-plan)
- The implementation decision should be: **Forge-owned domain model first; optional NetworkX as an internal algorithm adapter; LlamaIndex and Graphify only as measured prototype comparators; reject GraphRAG, Graphiti, and Cognee for the one-PRD production path.** This directly matches D-045 and the current roadmap. [Forge decisions, D-045](../../docs/DECISIONS.md#d-045-make-evidence-backed-deep-review-the-primary-experience); [Forge roadmap](../../docs/ROADMAP.md#current-build)

### Gaps

- The exact closed-set contradiction taxonomy and tie-breaking policy still need specification and human review.
- Forge needs a labelled golden set with quote pairs, finding type, duplicate grouping, priority, and “not a contradiction” hard negatives. The current roadmap names the MicroDrama PRD as the first golden case. [Forge roadmap](../../docs/ROADMAP.md#current-build)
- Acceptance thresholds for contradiction precision, recall, quote correctness, duplicate rate, priority agreement, and actionability have not yet been defined.
- It remains to test whether deterministic blocking misses conflicts expressed through aliases or implicit scope. Embeddings may be evaluated later as an advisory candidate-expansion mechanism, but they cannot replace exhaustive extraction or prove absence.
