# Document Intelligence for Forge's PRD Reviewer

Research cutoff: **2026-09-25**. All web sources linked below were accessed on **2026-09-25**. Local Forge source and canonical documents were inspected at the workspace revision present on that date. “Lossless” is used narrowly: lossless serialization of a parser's normalized object is not the same as lossless recovery of the original PDF/DOCX, layout, styling, or source bytes.

## What exact structure, hierarchy, and provenance does each project preserve?

### Takeaway

Docling has the closest documented representation to Forge's target: a typed document tree plus flat typed collections, reading order, page/bounding-box/character-span provenance, structured tables, pictures, and lossless serialization of the resulting `DoclingDocument`. PyMuPDF4LLM now has a strong PDF-only page/layout JSON that is much richer than Forge's current page text, but it is not a cross-format document tree. Marker and Unstructured preserve useful structure and provenance but are optimized around conversion/RAG elements rather than an evidence-authority representation. MarkItDown is deliberately a token-efficient Markdown converter and does not preserve the provenance Forge needs.

### Cited Findings

#### Forge's actual baseline

- Forge's PDF adapter creates one `SourceBlock` per page from `page.get_text("text")`; the only source location is the one-based page. Any page with an embedded image or vector drawing gets one page-level visual marker, regardless of how many distinct figures or diagrams occur on the page. [Forge PDF ingestion](https://github.com/amanchawla-wynk/forge/blob/main/src/forge/ingest/document.py#L73-L91)
- Forge's DOCX adapter walks body paragraphs and tables in body order. Heading-style paragraphs update one current section string; ordinary paragraphs become blocks; each table row becomes a pipe-joined string after empty cells are discarded. Headers and footers are appended after the body, and image relationships are inventoried without placement, caption, surrounding section, dimensions, or drawing semantics. [Forge DOCX ingestion](https://github.com/amanchawla-wynk/forge/blob/main/src/forge/ingest/document.py#L94-L167)
- A Forge `SourceBlock` can carry `page`, `section`, `parent_id`, and split offsets, but current PDF blocks do not carry bounding boxes or hierarchy and current DOCX blocks do not carry pages, table coordinates, list depth, links, or image anchors. Quote verification succeeds only when the quote can be found wholly inside one normalized block. [Forge normalized models](https://github.com/amanchawla-wynk/forge/blob/main/src/forge/ingest/models.py#L14-L23); [Forge quote location](https://github.com/amanchawla-wynk/forge/blob/main/src/forge/ingest/models.py#L89-L110)
- Forge's oversized-block splitter preserves exact source offsets and overlap, and all blocks remain eligible for exhaustive batching. This behavior is part of Forge's evidence contract and must survive a parser change. [Forge batching](https://github.com/amanchawla-wynk/forge/blob/main/src/forge/ingest/batching.py#L22-L88); [Forge architecture](https://github.com/amanchawla-wynk/forge/blob/main/docs/ARCHITECTURE.md#dependency-strategy)
- The current binding ingestion defect is already measured: PDF line splitting fragments a multi-line requirement so a known mood rule survives only as `"last 30 days window (top 5"`, preventing candidate pairing and depressing proxy deep-review recall to 3/19. [Forge D-051](https://github.com/amanchawla-wynk/forge/blob/main/docs/DECISIONS.md#d-051-measure-deep-review-recall-before-adding-more-detectors)

#### Important DoclingDocument details

- `NodeItem` supplies `self_ref`, optional `parent`, ordered `children`, and a body/furniture content layer. `DocItem` adds an element label and a list of provenance records; floating items add captions, references, footnotes, and optional image data. [Docling Core node types](https://github.com/docling-project/docling-core/blob/main/docling_core/types/doc/items/node.py)
- `ProvenanceItem` records `page_no`, `bbox`, and `charspan`. This is substantially stronger than Forge's current PDF page-only and DOCX section-only evidence location, but the adapter must define whether `charspan` is against item text, normalized page text, or another backend artifact before relying on it for quote verification. [Docling Core node types](https://github.com/docling-project/docling-core/blob/main/docling_core/types/doc/items/node.py)
- `DoclingDocument` JSON keeps both a tree (`body`/`furniture`) and flat typed arrays referenced by JSON pointers. That apparent duplication is deliberate identity/reference structure, not prompt-ready text. [DoclingDocument concept](https://docling-project.github.io/docling/concepts/docling_document/); [Docling Core document type](https://github.com/docling-project/docling-core/blob/main/docling_core/types/doc/document.py)
- Docling's public format table calls JSON a “Lossless serialization of Docling Document.” It does not claim that PDF drawing operators, every DOCX style/run/revision, original byte streams, or pagination can be reconstructed. [Docling supported formats](https://docling-project.github.io/docling/usage/supported_formats/)
- PDF pictures generated by the standard pipeline are crops from rendered page images at the configured scale, not the original embedded PDF image objects. DOCX/PPTX images can be extracted from their original OOXML binary blobs. [Docling PDF picture pipeline](https://github.com/docling-project/docling/blob/main/docling/pipeline/standard_pdf_pipeline.py); [Docling PowerPoint backend](https://github.com/docling-project/docling/blob/main/docling/backend/mspowerpoint_backend.py)
- Forge should not feed full Docling JSON to the reviewer model. Docling's serializers return text plus metadata about contributing components, and its native hierarchical/hybrid chunkers retain headings/captions and can split tables while repeating headers. Those APIs are useful implementation references, but Forge must continue exhaustive source eligibility rather than switching to retrieval-oriented chunk selection. [Docling serialization](https://docling-project.github.io/docling/concepts/serialization/); [Docling chunking](https://docling-project.github.io/docling/concepts/chunking/); [Forge scoring theory](https://github.com/amanchawla-wynk/forge/blob/main/docs/SCORING_THEORY.md#evidence-rule)
- `HierarchicalChunker` emits one chunk per detected document element by default, merges list items unless configured otherwise, and attaches relevant headings and captions. This is a useful semantic-boundary projection, but it is not a substitute for Forge's complete canonical item ledger. [Docling chunking](https://docling-project.github.io/docling/concepts/chunking/)
- `HybridChunker` starts from hierarchical chunks, splits only token-overflowing chunks, and optionally merges adjacent undersized chunks when headings and captions match. It repeats table headers across table splits by default. The tokenizer is caller-selected, so using it in Forge would couple chunk boundaries to a tokenizer configuration that must be fingerprinted and must not determine whether source content is reviewed. [Docling chunking](https://docling-project.github.io/docling/concepts/chunking/)
- Docling's chunkers return text plus metadata and offer `contextualize()` for model-facing serialization. Forge can borrow their semantic boundaries and table-header behavior, but should retain `semchunk` or another offset-preserving final split wherever exact child spans are required. [Docling chunking](https://docling-project.github.io/docling/concepts/chunking/); [Forge architecture](https://github.com/amanchawla-wynk/forge/blob/main/docs/ARCHITECTURE.md#dependency-strategy)

### Inferences

- **Docling is the only candidate worth testing as a common PDF/DOCX canonical sidecar.** Its tree and typed items can address Forge's current loss of multi-line units, table structure, image placement, and section relationships without making the parser a scoring authority. The Forge-facing `SourceBlock` projection should remain smaller and exact-quote-friendly, while the complete `DoclingDocument` stays available for provenance and advisory analysis. This inference follows from Docling's documented model and Forge's evidence boundary. [DoclingDocument concept](https://docling-project.github.io/docling/concepts/docling_document/); [Forge architecture](https://github.com/amanchawla-wynk/forge/blob/main/docs/ARCHITECTURE.md#dependency-strategy)
- **PyMuPDF4LLM is the most useful control, not a complete solution.** It may fix PDF reading order, headings, tables, links, and region provenance with less adapter work than Docling, while leaving DOCX unchanged. Its JSON's duplicated `boxes` and `fulltext` should be retained only as an audit sidecar; one canonical text path must feed evidence and prompts. [PyMuPDF4LLM JSON schema](https://docs.pdf4llm.com/python/reference/JSON-schema)
- **No parser should make diagrams scoreable merely by describing them.** A picture crop, classification, caption, or vision-model description is useful advisory material, but it does not satisfy Forge's exact-quote evidence rule unless OCR text is inserted as a separately provenanced evidence block. [Forge scoring theory](https://github.com/amanchawla-wynk/forge/blob/main/docs/SCORING_THEORY.md#evidence-rule); [Forge D-017](https://github.com/amanchawla-wynk/forge/blob/main/docs/DECISIONS.md#d-017-separate-text-evidence-from-visual-interpretation)
- **DOCX page numbers remain non-authoritative.** Even if a parser emits them, pagination depends on renderer state and explicit/rendered page breaks. Forge should preserve DOCX package order, section/heading ancestry, table/list position, and relationship anchors, and treat page as optional display metadata. [Forge scoring theory](https://github.com/amanchawla-wynk/forge/blob/main/docs/SCORING_THEORY.md#evidence-rule); [Unstructured DOCX behavior](https://docs.unstructured.io/open-source/core-functionality/partitioning#partition_docx)

### Gaps

- The reviewed Docling documentation does not establish a uniform, tested contract for retaining hyperlink anchor text and target URLs across both PDF and DOCX backends. This needs a fixture-level test.
- “Lossless JSON” does not answer whether a quote can always be re-located in normalized text after table reconstruction, OCR correction, ligature normalization, or formula conversion. Forge must measure this directly.
- None of the projects documents accuracy specifically on product-requirements documents with the same table-heavy, link-heavy, diagram-heavy patterns as Forge's 20–30 page PRDs.

## Which projects require models, services, GPUs, providers, or invasive deployment changes?

### Takeaway

All six can run locally in some form, but “self-hosted” does not mean “model-free” or “small.” Docling's standard PDF path uses local layout/table/OCR models and PyTorch but needs no provider or GPU. Marker is the most invasive: local Surya inference infrastructure, PyTorch, model-weight licensing, and provider SDKs are part of its package even when the optional external-LLM path is disabled. Unstructured's useful high-resolution PDF path adds models plus Poppler/Tesseract and has default telemetry. PyMuPDF4LLM is CPU-only and operationally narrow but brings an AGPL/commercial license and a roughly 43 MB platform wheel for its packaged GNN layout model. MarkItDown is light and local by default, but its richer paths are Azure/LLM integrations rather than a provenance-preserving local model.

#### Context and token implications

- Forge has already observed an approximately 83,000-character extraction prompt for one real PRD. Repeating that prompt drove the checkpoint-remediation design. Parser output must therefore be judged by model-facing serialized size and batch behavior, not only extraction accuracy. [Forge D-040](https://github.com/amanchawla-wynk/forge/blob/main/docs/DECISIONS.md#d-040-checkpoint-remediation-and-extract-only-answer-deltas)
- Docling's full JSON contains a tree, reference arrays, provenance, page records, and potentially images. It is an audit/canonical representation, not an efficient prompt format. Its hierarchical and hybrid chunkers can preserve headings/captions and repeat table headers, but Forge must continue to process every source item rather than use retrieval. [DoclingDocument concept](https://docling-project.github.io/docling/concepts/docling_document/); [Docling chunking](https://docling-project.github.io/docling/concepts/chunking/)
- Marker JSON can contain base64 images and recursively repeated HTML references; PyMuPDF4LLM JSON contains both layout boxes and raw `fulltext`, often duplicating textual content; Unstructured's chunk objects may carry encoded `orig_elements`; all three would inflate model context if passed through directly. [Marker JSON output](https://github.com/datalab-to/marker#json); [PyMuPDF4LLM JSON schema](https://docs.pdf4llm.com/python/reference/JSON-schema); [Unstructured elements](https://docs.unstructured.io/open-source/concepts/document-elements)
- MarkItDown explicitly argues that Markdown is token-efficient, but it achieves that compactness by omitting the item-level source mapping Forge needs. [MarkItDown README](https://github.com/microsoft/markitdown#why-markdown)
- PyMuPDF4LLM's page chunks offer a useful middle layer: page text plus box character ranges, TOC items, table/image/graphic inventories, and optional ordered words. An adapter can keep detailed JSON out of prompts while retaining it for audit. [PyMuPDF4LLM API](https://pymupdf.readthedocs.io/en/latest/pymupdf4llm/api.html)

### Inferences

- “Model-independent reviewer” should mean Forge remains independent of an LLM provider and model API. It need not prohibit deterministic local document-analysis models, but model files, licenses, cold-start downloads, hashes, and device behavior must be explicit and reproducible. Docling can meet that interpretation; Marker cannot enter Forge's default dependency graph without violating the current provider-SDK boundary. [Docling local execution](https://github.com/docling-project/docling); [Marker PyPI metadata](https://pypi.org/project/marker-pdf/); [Forge D-006](https://github.com/amanchawla-wynk/forge/blob/main/docs/DECISIONS.md#d-006-client-llm-only)
- If Docling wins, the least invasive shape is an **optional parser adapter** with pinned package/model versions and a preflight/download command, while the current parser remains a deterministic fallback during rollout. This is not backward-compatibility for its own sake: existing source hashes, review sessions, evidence locations, and final reassessments require parser-version identity to prevent silent document drift. [Forge review identity](https://github.com/amanchawla-wynk/forge/blob/main/docs/DECISIONS.md#d-042-forge-owns-review-identity-and-new-chats-resume-explicit)
- Docling MCP should not be placed between Forge's MCP tools and ingestion. Direct library embedding avoids a second MCP capability/security surface, an opaque cache key, and remote-mode credentials while preserving access to the same `DoclingDocument`. [Docling MCP conversion source](https://github.com/docling-project/docling-mcp/blob/main/docling_mcp/tools/conversion.py); [Forge portability](https://github.com/amanchawla-wynk/forge/blob/main/docs/ARCHITECTURE.md#portability)
- Parser JSON should never be the extraction prompt. Forge should store one normalized sidecar and derive compact, stable source blocks with explicit item IDs, heading ancestry, page/section, and exact normalized character ranges. This keeps prompt tokens proportional to evidence text rather than metadata and images. [Forge architecture](https://github.com/amanchawla-wynk/forge/blob/main/docs/ARCHITECTURE.md#dependency-strategy)

### Gaps

- Published pages reviewed here do not provide comparable cold-start model-download bytes, peak resident memory, or latency for a 20–30 page business PDF/DOCX on Forge's target CPU hardware. The benchmark must collect them.
- Docling model artifacts have individual licenses. A dependency decision requires an SBOM/license review of the exact selected standard-pipeline models, not only the MIT library license.
- The legal acceptability of AGPL dependencies or an Artifex commercial license is organization-specific and cannot be decided from technical research.

## What should Forge adopt, benchmark, borrow, and what narrow benchmark proves value?

### Takeaway

Do not replace ingestion blindly. Run a two-candidate benchmark: **Docling as the cross-format structured adapter** and **PyMuPDF4LLM as the low-invasiveness PDF control**, both against Forge's current parser. Include Marker only as an offline accuracy ceiling if licensing and setup time permit. Borrow Unstructured's identity/provenance ideas. Do not integrate Docling MCP or MarkItDown. Adoption is justified only if a candidate fixes the known multi-line/table/reading-order defects without reducing exact quote verification, exhaustive coverage, determinism, or acceptable token/runtime behavior.

#### What Docling MCP adds versus embedding Docling

- The library gives Forge direct access to `DocumentConverter`, `ConversionResult.document`, serializers, chunkers, and the complete in-process `DoclingDocument`. [Docling quickstart](https://github.com/docling-project/docling#quickstart); [Docling architecture](https://docling-project.github.io/docling/concepts/architecture/)
- Docling MCP adds stdio/SSE/streamable-HTTP transport, conversion of files/URLs/directories, an in-memory LRU document cache addressed by a generated document key, cache inspection/eviction, generation and manipulation tools, remote Docling Serve mode, and optional RAG/structured-extraction tool groups. [Docling MCP README](https://github.com/docling-project/docling-mcp); [conversion tools](https://github.com/docling-project/docling-mcp/blob/main/docling_mcp/tools/conversion.py); [server tool groups](https://github.com/docling-project/docling-mcp/blob/main/docling_mcp/servers/mcp_server.py)
- Those additions are useful when a general-purpose agent needs an independent document service. They do not improve conversion fidelity. In Forge they would duplicate MCP transport, introduce a second cache identity that is not Forge's source hash, complicate lifecycle/error handling, and make remote mode introduce a service API key that direct local embedding does not need. [Docling MCP README](https://github.com/docling-project/docling-mcp); [Forge boundary](https://github.com/amanchawla-wynk/forge/blob/main/docs/ARCHITECTURE.md#boundary)

#### Narrow benchmark proposal

The following is a **proposed Forge experiment**, not a documented upstream benchmark result.

1. **Candidates:** current Forge parser; Docling standard local pipeline with fixed options/model revisions; PyMuPDF4LLM default layout JSON; optionally Marker `fast --disable_ocr` and `balanced` as non-production comparators. Keep generative LLM correction, remote services, and picture-description models off so this tests ingestion rather than provider quality.
2. **Corpus:** four 20–30 page cases: the known 21-page MicroDrama PDF; one representative real DOCX with headings, body tables, headers/footers, links, and embedded images; a PDF export of that same DOCX for cross-format comparison; and one synthetic adversarial document containing two columns, a multi-page table, merged cells, repeated headers, inline links, a diagram with caption, raster text, vector drawing, lists, and deliberate multi-line requirements. The existing real-DOCX run demonstrates Forge has encountered 397 blocks, 26 sections, and 24 images; the known PDF exposes the current multiline-claim defect. [Forge roadmap](https://github.com/amanchawla-wynk/forge/blob/main/docs/ROADMAP.md#completed); [Forge D-051](https://github.com/amanchawla-wynk/forge/blob/main/docs/DECISIONS.md#d-051-measure-deep-review-recall-before-adding-more-detectors)
3. **Gold annotations:** manually mark approximately 100 evidence atoms across the four files: paragraph/list text, heading ancestry, adjacent reading-order pairs, complete multi-line requirements, table cells and spans, links with targets, visual anchors/captions, headers/footers, and PDF page/bbox. For DOCX, gold package order and heading ancestry rather than visual page number, consistent with Forge's current evidence policy. [Forge scoring theory](https://github.com/amanchawla-wynk/forge/blob/main/docs/SCORING_THEORY.md#evidence-rule)
4. **Primary evidence metrics:** exact normalized text recall; percentage of gold quotes locatable wholly within one projected `SourceBlock`; duplicated or hallucinated text rate; stable block IDs and canonical output hash over three runs; correct PDF page and item location; exhaustive inclusion of every projected block in a batch.
5. **Structure metrics:** heading-parent accuracy; reading-order adjacent-pair accuracy; complete multi-line requirement recall; list nesting; table cell text accuracy, row/column accuracy, merged-cell/span accuracy, and cross-page table continuity; link anchor/target recall; visual detection and correct placement/caption association.
6. **Forge outcome metric:** rerun `forge-proxy-diagnostics` with only ingestion changed and report candidate coverage, finding recall, blocker recall, hard-negative violations, and whether the page-16 mood rule becomes one usable claim. This directly tests the measured bottleneck instead of relying on generic PDF benchmark scores. [Forge D-051](https://github.com/amanchawla-wynk/forge/blob/main/docs/DECISIONS.md#d-051-measure-deep-review-recall-before-adding-more-detectors)
7. **Cost metrics:** install size; cold model bytes/network requests; cold and warm wall time; peak RSS; CPU/GPU use; normalized text characters; prompt characters and tokenizer counts; extraction batch count; sidecar JSON size with and without images; failure behavior offline.
8. **Security/deployment checks:** no provider keys; no document-content network calls; telemetry disabled; model/cache paths controllable; exact package/model/license inventory; local path handling no broader than current Forge; parser/version/options included in the normalization fingerprint.

#### Proposed adoption gates

- **Evidence gate:** no reduction in gold quote locatability or unsupported-quote rejection versus current Forge; every scoreable quote still maps to a stable block and exact normalized span.
- **Known-defect gate:** the full multi-line mood requirement must survive as one item or as deterministically joinable sibling items and must enter the intended candidate pair.
- **Structure gate:** a material, preregistered improvement over current Forge on heading ancestry, reading order, and tables. Set the numeric threshold only after annotating the small corpus, before running candidate outputs.
- **Safety gate:** zero new hard-negative deep-review violations and no visual interpretation entering numeric scoring.
- **Token gate:** compact prompt projection should not exceed the current parser's model-facing tokens by more than a preregistered tolerance; rich JSON/image bytes remain out of extraction prompts.
- **Operational gate:** repeatable offline execution on supported developer hardware with pinned artifacts, acceptable cold/warm latency and memory, and a license compatible with Forge distribution.
- **Complexity gate:** adapter code must preserve Forge-owned `SourceBlock` identity, exhaustive batching, quote verification, source hash/fingerprint behavior, visual provenance, and parser-version audit. A candidate that only produces prettier Markdown does not pass.

### Inferences

- **Likely best production outcome:** Docling for both PDF and DOCX if it passes, with a compact Forge projection and preserved raw `DoclingDocument` JSON sidecar. If it fails deployment/token gates but PyMuPDF4LLM clears the PDF quality gate, use PyMuPDF4LLM only for PDF and make smaller targeted improvements to the current DOCX adapter.
- **Likely lowest-risk first spike:** implement no production dependency. Write one developer-only comparison script that converts each fixture, projects candidate outputs into a common evaluation schema, and emits metrics. This makes the adoption decision reversible and consistent with Forge's prior framework-spike practice. [Forge D-050](https://github.com/amanchawla-wynk/forge/blob/main/docs/DECISIONS.md#d-050-complete-the-deterministic-core-extend-the-taxonomy-and-defer-both-frameworks)
- **Do not evaluate by downstream score alone.** A parser can change a readiness score by omitting text, joining unrelated cells, or making quotes unverifiable. Structure/provenance accuracy and negative invariants must be reported before any score movement is interpreted as improvement. [Forge scoring theory](https://github.com/amanchawla-wynk/forge/blob/main/docs/SCORING_THEORY.md#known-gaming-and-failure-modes)
- **Do not adopt upstream chunk selection.** Docling's chunkers and Unstructured's chunks may inform safe boundaries and metadata, but Forge must include every normalized block in at least one extraction batch. [Forge scoring theory](https://github.com/amanchawla-wynk/forge/blob/main/docs/SCORING_THEORY.md#evidence-rule)

### Gaps

- The benchmark cannot be completed from the checked-in repository because the representative PDF/DOCX binaries are not present in this workspace; the research notes refer to them, but an authorized local corpus path is needed.
- Human gold annotations for reading order, table spans, image anchors, and links do not yet exist. Generic public leaderboards cannot substitute for this PRD-specific set.
- A final **ADOPT** decision requires measured results plus license review. The current evidence supports **BENCHMARK**, not replacement.
