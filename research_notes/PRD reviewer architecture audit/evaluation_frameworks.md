# Evaluation Frameworks for Forge: DeepEval, Ragas, and Promptfoo

Research snapshot: 2026-09-25. All linked upstream sources were accessed on 2026-09-25. Version observations refer to what the official repositories exposed on that date: DeepEval's latest GitHub release was Python 4.2.4 while `main` declared 4.2.6, Ragas' latest release was 0.4.3, and Promptfoo's latest release was 0.123.1. [DeepEval release](https://github.com/confident-ai/deepeval/releases/tag/python-v4.2.4); [DeepEval `main` package metadata](https://github.com/confident-ai/deepeval/blob/main/pyproject.toml); [Ragas release](https://github.com/vibrantlabsai/ragas/releases/tag/v0.4.3); [Promptfoo release](https://github.com/promptfoo/promptfoo/releases/tag/0.123.1)

This audit distinguishes two different objects of evaluation:

- **Evaluating a PRD at runtime** means normalizing one document, borrowing the connected client's model only for bounded extraction or classification, mechanically verifying source evidence, and applying Forge's versioned rubric and deterministic Python scoring. [Forge architecture](../../docs/ARCHITECTURE.md#boundary); [Forge scoring theory](../../docs/SCORING_THEORY.md#extraction-before-judgment)
- **Evaluating Forge offline** means testing whether Forge's extraction, readiness verdicts, deep-review findings, remediation behavior, stability, and anti-gaming properties agree with independent labels and fixed expectations. It is a developer workflow, not an MCP assessment tool. [Forge architecture](../../docs/ARCHITECTURE.md#offline-calibration); [Forge validation plan](../../docs/SCORING_THEORY.md#validation-plan)

## Which framework belongs in runtime PRD evaluation, offline Forge evaluation, both, or neither?

### Takeaway

None belongs in Forge's runtime PRD-scoring path. DeepEval G-Eval is worth a controlled **BENCHMARK** as an offline secondary judge, DeepEval DAGMetric is **BORROW IDEAS**, Ragas is **NOT NEEDED**, and Promptfoo is the strongest **BENCHMARK** candidate for an external offline regression/matrix runner. Promptfoo should be adopted only if a spike proves that its orchestration and reports reduce maintenance without replacing Forge's human-label, provenance, or deterministic-scoring authorities. [DeepEval G-Eval docs](https://deepeval.com/docs/metrics-llm-evals); [DeepEval DAG docs](https://deepeval.com/docs/metrics-dag); [Ragas metrics overview](https://docs.ragas.io/en/stable/concepts/metrics/overview/); [Promptfoo CLI](https://www.promptfoo.dev/docs/usage/command-line/)

### Cited Findings

#### Decision matrix

| Candidate | Runtime PRD evaluation | Offline evaluation/testing of Forge | Classification | Decision | Why |
|---|---|---|---|---|---|
| DeepEval G-Eval | No | Yes, as a secondary experiment only | Offline only | **BENCHMARK** | It accepts arbitrary criteria, fixed evaluation steps, score rubrics, strict binary mode, custom judge models, and returns a score plus reason. It is explicitly LLM-as-judge and non-deterministic, so it cannot own readiness points or serve as ground truth. [G-Eval docs](https://deepeval.com/docs/metrics-llm-evals); [G-Eval source](https://github.com/confident-ai/deepeval/blob/main/deepeval/metrics/g_eval/g_eval.py) |
| DeepEval DAGMetric | No | Limited; useful mainly as a comparison against a fixed labelled set | Offline only | **BORROW IDEAS** | Explicit branches, terminal outcomes, and verbose execution paths are useful patterns. However, DeepEval states that task and judgement nodes still use a model and can vary; only graph structure and terminal score mapping are controlled. Forge already has stronger deterministic scoring after verified extraction. [DAG docs](https://deepeval.com/docs/metrics-dag); [DAG node source](https://github.com/confident-ai/deepeval/blob/main/deepeval/metrics/dag/nodes.py); [Forge scoring theory](../../docs/SCORING_THEORY.md#aggregation) |
| Ragas | No | Technically possible, but little incremental value over Forge's existing evaluators | Offline only in capability; no recommended dependency | **NOT NEEDED** | Ragas is optimized for RAG/LLM application samples, contexts, answers, references, and application metrics. Its custom and non-LLM metrics are flexible, but Forge already owns domain-specific band, criterion, evidence, deep-review, and reviewer-agreement evaluators. [Ragas README](https://github.com/vibrantlabsai/ragas); [Ragas sample schema](https://docs.ragas.io/en/stable/references/evaluation_schema/); [Forge offline calibration](../../docs/ARCHITECTURE.md#offline-calibration) |
| Promptfoo | No | Yes | Offline only | **BENCHMARK** | It is designed as a local CLI/library and CI runner, can execute supplied outputs or custom scripts, supports deterministic and model-graded assertions, repeats, caching controls, exports, failure exit codes, and provider matrices. Its Node/provider dependency surface and generic result model mean it should wrap Forge tests, not become Forge's domain evaluator. [Promptfoo README](https://github.com/promptfoo/promptfoo); [deterministic assertions](https://www.promptfoo.dev/docs/configuration/expected-outputs/deterministic/); [CLI](https://www.promptfoo.dev/docs/usage/command-line/) |

#### Why no runtime adoption

- Forge's runtime claim is not "an LLM assigns a quality score." The model extracts fields and verbatim evidence; Python verifies evidence, derives `present`/`partial`/`absent`/`not_applicable`, applies hidden weights and gates, and selects the final band. [Forge scoring theory](../../docs/SCORING_THEORY.md#extraction-before-judgment); [aggregation](../../docs/SCORING_THEORY.md#aggregation)
- DeepEval G-Eval generates or consumes evaluation steps and then asks a judge model for a score and reason. Even with explicit steps, a rubric, strict mode, or temperature controls, the score remains model-produced rather than mechanically derived from verified fields. [G-Eval calculation](https://deepeval.com/docs/metrics-llm-evals#how-is-it-calculated); [G-Eval source](https://github.com/confident-ai/deepeval/blob/main/deepeval/metrics/g_eval/g_eval.py)
- DeepEval DAGMetric maps a model-selected branch to a developer-selected terminal score. Its own FAQ says a DAG does not make every evaluation deterministic because task and judgement nodes still use a model. This is weaker than Forge's requirement that identical verified extraction inputs always produce identical scores. [DAG FAQ](https://deepeval.com/docs/metrics-dag#faqs); [Forge success criteria](../../docs/PRODUCT.md#success-criteria)
- Ragas explicitly separates LLM metrics, which it describes as somewhat non-deterministic, from non-LLM metrics such as string similarity and BLEU. Neither category supplies Forge's document normalization, exact quote relocation, criterion-bound provenance, gate semantics, or versioned readiness bands. [Ragas metrics overview](https://docs.ragas.io/en/stable/concepts/metrics/overview/); [Forge evidence rule](../../docs/SCORING_THEORY.md#evidence-rule)
- Promptfoo's model-graded `llm-rubric` and G-Eval assertions let the grading model return scores. Its deterministic assertions can validate strings, JSON schemas, scripts, and traces, but they are generic test primitives rather than a PRD evidence model. [Promptfoo LLM rubric](https://www.promptfoo.dev/docs/configuration/expected-outputs/model-graded/llm-rubric/); [Promptfoo G-Eval](https://www.promptfoo.dev/docs/configuration/expected-outputs/model-graded/g-eval/); [deterministic assertions](https://www.promptfoo.dev/docs/configuration/expected-outputs/deterministic/)
- Adding any of these as the runtime scorer would create two authorities: Forge's verified rubric engine and a framework's score/pass result. The project's architecture makes Forge scoring code authoritative and keeps model outputs untrusted until schema and evidence validation pass. [Forge trust boundaries](../../docs/ARCHITECTURE.md#trust-boundaries)

[Promptfoo CLI](https://www.promptfoo.dev/docs/usage/command-line/); [Promptfoo caching](https://www.promptfoo.dev/docs/configuration/caching/); [custom provider](https://www.promptfoo.dev/docs/providers/custom-api/) |

### Inferences

- The recommended boundary is **Forge evaluates PRDs; an external harness may evaluate Forge**. None of the three should be imported by `forge.score`, `forge.extract`, ingestion, MCP tools, or the default package. [Forge architecture](../../docs/ARCHITECTURE.md#boundary); [dependency strategy](../../docs/ARCHITECTURE.md#dependency-strategy)
- G-Eval is most defensible for a narrow qualitative study such as "does the generated finding state an actionable author decision?" after the finding and source evidence have been frozen. It is not defensible for deciding whether the source quote exists, whether a required field is present, or what readiness band applies. [G-Eval docs](https://deepeval.com/docs/metrics-llm-evals); [Forge evidence rule](../../docs/SCORING_THEORY.md#evidence-rule)
- DAGMetric's valuable idea is not "replace Forge scoring with a DAG"; it is "make every decision path and terminal mapping inspectable." Forge already does this more safely through fixed rubric verdict credits, gates, stable question ordering, closed-set classifications, and deterministic reports. [DAG docs](https://deepeval.com/docs/metrics-dag); [Forge scoring theory](../../docs/SCORING_THEORY.md#aggregation); [output restraint](../../docs/SCORING_THEORY.md#output-restraint)
- Promptfoo should be spiked against the existing authored regression corpus and offline evaluators, not against live PRDs first. Success means less test-matrix/reporting code with identical Forge-calculated verdicts and no new runtime dependency; failure means retain pytest plus Forge's current CLIs. [Forge regression corpus](../../docs/SCORING_THEORY.md#regression-corpus); [Promptfoo custom scripts](https://www.promptfoo.dev/docs/providers/custom-script/)

### Gaps

- None of the three projects publishes a first-party benchmark for PRD readiness, exact source-span verification, contradiction detection on long PRDs, or one-question remediation usefulness.
- No representative Forge corpus was run through these tools during this desk audit, so relative latency, judge stability, installed size, and maintenance cost remain unmeasured.
- DeepEval's repository state was ahead of its latest GitHub release on the access date; any spike must pin either the released 4.2.4 tag or a specific commit, not an ambiguous `main` version. [DeepEval release](https://github.com/confident-ai/deepeval/releases/tag/python-v4.2.4); [DeepEval `main` metadata](https://github.com/confident-ai/deepeval/blob/main/pyproject.toml)

## How do licenses, runtimes, providers, rubrics, provenance, determinism, and deployment compare?

### Takeaway

All three are permissively licensed, but permissive licensing does not make them architecturally lightweight. DeepEval and Ragas are Python packages with mandatory OpenAI-facing dependencies in their base metadata; Promptfoo is a Node 22 CLI with a large provider-aware dependency surface. All support custom evaluation criteria, but none natively enforces Forge's exact source-location and criterion-bound evidence contract. [DeepEval metadata](https://github.com/confident-ai/deepeval/blob/main/pyproject.toml); [Ragas metadata](https://github.com/vibrantlabsai/ragas/blob/main/pyproject.toml); [Promptfoo metadata](https://github.com/promptfoo/promptfoo/blob/main/package.json)

#### Provider and model dependencies

- DeepEval G-Eval's `model` accepts an OpenAI model name or a custom `DeepEvalBaseLLM`, and its custom-model contract requires synchronous/asynchronous generation plus schema-aware structured output for full metric compatibility. G-Eval's probability-weighted scoring is available when the model exposes suitable log probabilities; otherwise custom models fall back to the raw generated score. [G-Eval parameters and calculation](https://deepeval.com/docs/metrics-llm-evals); [custom LLM guide](https://deepeval.com/guides/guides-using-custom-llms)
- DeepEval DAGMetric accepts an evaluation model and, in the audited 4.2 line, an optional TypeSafe AI "Jev" model. The release notes describe Jev as an opt-in typed-decision service requiring `typesafe-sdk` and `TYPESAFE_API_KEY`; DAG task nodes still need an LLM. This is a new external provider dependency, not a path to provider-free Forge core. [DeepEval 4.2.4 release](https://github.com/confident-ai/deepeval/releases/tag/python-v4.2.4); [DAG docs](https://deepeval.com/docs/metrics-dag)
- Ragas' `MetricWithLLM.init` raises when no LLM is supplied. Its current package metadata includes OpenAI and LangChain/OpenAI packages in the base install, while its non-LLM metric classes can run deterministically without a model. [Ragas metric reference](https://docs.ragas.io/en/stable/references/metrics/); [package metadata](https://github.com/vibrantlabsai/ragas/blob/main/pyproject.toml)
- Promptfoo model-graded assertions select a grader from available credentials by default, but an assertion can override the provider, including with a custom local provider. Its deterministic assertions and Python/JavaScript functions need no grader model. [LLM rubric provider rules](https://www.promptfoo.dev/docs/configuration/expected-outputs/model-graded/llm-rubric/); [custom provider](https://www.promptfoo.dev/docs/providers/custom-api/); [deterministic assertions](https://www.promptfoo.dev/docs/configuration/expected-outputs/deterministic/)
- "Runs locally" does not mean "no data leaves the machine": any configured hosted judge receives the evaluation material. Promptfoo's README says orchestration runs locally, while its own quick start notes that most LLM providers require an API key. [Promptfoo README](https://github.com/promptfoo/promptfoo)

| Project | Custom criteria/rubric mechanism | Fit to Forge's rubric |
|---|---|---|

[G-Eval docs](https://deepeval.com/docs/metrics-llm-evals) | Expressive enough to imitate a PRD criterion, but the judge still owns the score. Forge requires the rubric to declare fields and objective constraints while Python derives credit after evidence verification. [Forge scoring theory](../../docs/SCORING_THEORY.md#extraction-before-judgment) |
| DeepEval DAGMetric | Developer-defined task nodes, binary/non-binary judgement nodes, closed verdict labels, branches, terminal 0-10 scores, and nested metrics. [DAG docs](https://deepeval.com/docs/metrics-dag) | Similar visual shape to gates and closed-set decisions, but model-selected branches are not acceptable as the numeric scoring authority. | Ragas | Custom discrete, numeric, and ranking metrics; LLM-backed discrete/numeric prompts; sample-level rubric fields; customizable prompts and examples; metric alignment/validation against labelled data. | Promptfoo | Exact, substring, regex, JSON-schema, similarity, script, webhook, trace, LLM-rubric, and G-Eval assertions; custom grader prompts/providers; thresholds and grouped assertions. Poor as the contract itself because generic pass/score aggregation does not encode Forge's source, criterion, calibration, and band semantics. |

#### Evidence and provenance fit

- DeepEval G-Eval returns a normalized score, a generated reason, evaluation steps, and optional verbose logs. Its test case fields can include context and expected output, but the metric does not require the reason to quote a mechanically relocatable span. [G-Eval docs](https://deepeval.com/docs/metrics-llm-evals); [G-Eval source](https://github.com/confident-ai/deepeval/blob/main/deepeval/metrics/g_eval/g_eval.py)
- DeepEval DAG verbose logs expose task output, judgement verdict/reason, and selected terminal result. The source labels task output as downstream "evidence," but task nodes call the evaluation model to generate that output; this is generated intermediate state, not Forge-grade source provenance. [DAG docs](https://deepeval.com/docs/metrics-dag#dag-node-types); [DAG node source](https://github.com/confident-ai/deepeval/blob/main/deepeval/metrics/dag/nodes.py)
- Ragas' `SingleTurnSample` can carry retrieved/reference contexts and context IDs, and `EvaluationResult` retains the original dataset, score rows, traces, and a run id. This is useful experiment provenance, but its standard schema has no normalized-document block id, page/section/offset span, exact-quote relocation result, criterion-bound supplemental source, or taxonomy-cell identity. [Ragas schema](https://docs.ragas.io/en/stable/references/evaluation_schema/); [Forge evidence rule](../../docs/SCORING_THEORY.md#evidence-rule)
- Promptfoo preserves test variables, outputs, provider responses and metadata, assertion reasons, optional traces, eval records, and exports. Custom providers can report the actual prompt and arbitrary metadata such as trace IDs. These are useful run-level provenance hooks, but source-span proof must remain data produced and verified by Forge. [Custom provider response](https://www.promptfoo.dev/docs/providers/custom-api/); [Python assertion context](https://www.promptfoo.dev/docs/configuration/expected-outputs/python/); [CLI export](https://www.promptfoo.dev/docs/usage/command-line/)
- Promptfoo exports redact configuration secrets but may still contain prompts, outputs, variables, traces, and media, so PRD test artifacts require the same local-data handling as Forge corpora. [Promptfoo export warning](https://www.promptfoo.dev/docs/usage/command-line/#promptfoo-export)

#### Deterministic-scoring compatibility

| Mechanism | Deterministic in the Forge sense? | Safe role |
|---|---|---|
| DeepEval G-Eval explicit steps, rubric, strict mode | No. These constrain the judge but do not remove model-selected scoring; DeepEval explicitly calls G-Eval non-deterministic. [G-Eval docs](https://deepeval.com/docs/metrics-llm-evals#what-is-g-eval) | Offline sensitivity or qualitative benchmark only. |
| DeepEval DAG fixed branch scores | Partly. Terminal mapping is fixed; branch decisions and task outputs remain model-based and variable. [DAG docs](https://deepeval.com/docs/metrics-dag#faqs) | Offline comparison or design inspiration, never runtime band calculation. |
| Ragas non-LLM/custom Python metrics | Yes, if the custom function and inputs are deterministic. [Ragas metrics overview](https://docs.ragas.io/en/stable/concepts/metrics/overview/) | Could calculate generic test metrics, but Forge already has the domain implementation. |
| Ragas LLM metrics | No; Ragas explicitly describes them as somewhat non-deterministic. [Ragas metrics overview](https://docs.ragas.io/en/stable/concepts/metrics/overview/) | Offline secondary judge only. |
| Promptfoo exact/schema/script assertions | Yes, subject to deterministic user code and inputs. [Deterministic assertions](https://www.promptfoo.dev/docs/configuration/expected-outputs/deterministic/); [Python assertions](https://www.promptfoo.dev/docs/configuration/expected-outputs/python/) | External regression assertions around Forge. |
| Promptfoo model-graded assertions | No. Temperature zero and caching can improve repeatability or replay, but they do not make a model judgement a deterministic fact. [LLM rubric settings](https://www.promptfoo.dev/docs/configuration/expected-outputs/model-graded/llm-rubric/#setting-grader-parameters-temperature-etc); [caching](https://www.promptfoo.dev/docs/configuration/caching/) | Offline judge experiments with model/version metadata and repeats. |

#### Operational behavior relevant to an offline harness

- Promptfoo caches successful provider responses to disk for 14 days by default. Repeat indices use separate cache namespaces; `--no-cache` is required when measuring fresh model variance or latency. [Promptfoo caching](https://www.promptfoo.dev/docs/configuration/caching/)
- Promptfoo can take precomputed model outputs with `--model-outputs`, repeat tests, export JSON/JSONL/JUnit and other formats, return a failing process exit code, and avoid persistence with `--no-write`. These features fit CI and frozen-output evaluation without forcing Promptfoo to invoke a provider. [Promptfoo CLI](https://www.promptfoo.dev/docs/usage/command-line/)
- Promptfoo telemetry is enabled by default, excludes prompts/outputs/test cases/API keys according to its docs, and can be disabled with `PROMPTFOO_DISABLE_TELEMETRY=1`; update checks can be disabled separately. A Forge benchmark should disable both for hermetic CI. [Promptfoo telemetry](https://www.promptfoo.dev/docs/configuration/telemetry/)
- Ragas reports minimal anonymized analytics and provides `RAGAS_DO_NOT_TRACK=true`. A hermetic Forge benchmark should opt out. [Ragas analytics](https://github.com/vibrantlabsai/ragas#-open-analytics)
- DeepEval and Ragas can be isolated in Python dev environments, while Promptfoo is naturally isolated as a pinned Node CLI or container. None needs to be deployed as a service for the recommended experiments. [DeepEval package metadata](https://github.com/confident-ai/deepeval/blob/main/pyproject.toml); [Ragas package metadata](https://github.com/vibrantlabsai/ragas/blob/main/pyproject.toml); [Promptfoo installation/README](https://github.com/promptfoo/promptfoo)

### Inferences

- License risk is low for normal internal use, but dependency and data-flow risk is material. Apache-2.0 or MIT does not address provider SDKs, telemetry defaults, local caches, PRD content in exported results, or externally hosted judges. [DeepEval license](https://github.com/confident-ai/deepeval/blob/main/LICENSE.md); [Ragas license](https://github.com/vibrantlabsai/ragas/blob/main/LICENSE); [Promptfoo license](https://github.com/promptfoo/promptfoo/blob/main/LICENSE); [Promptfoo export warning](https://www.promptfoo.dev/docs/usage/command-line/#promptfoo-export)
- DeepEval's direct `openai` dependency and Ragas' direct OpenAI/LangChain dependencies make either inappropriate for Forge's default or core dependency groups even if a custom model adapter is used at runtime. The dependency itself would violate the intended "no provider SDK in MCP/core" packaging boundary. [DeepEval metadata](https://github.com/confident-ai/deepeval/blob/main/pyproject.toml); [Ragas metadata](https://github.com/vibrantlabsai/ragas/blob/main/pyproject.toml); [Forge D-006](../../docs/DECISIONS.md#d-006-client-llm-only)
- Promptfoo is safer as a process boundary than as a library dependency: its CLI can consume frozen outputs or call a thin Forge script, and all Node/provider packages remain outside Forge's Python distribution. [Promptfoo CLI](https://www.promptfoo.dev/docs/usage/command-line/); [custom script provider](https://www.promptfoo.dev/docs/providers/custom-script/)
- A model judge's `reason` is diagnostic evidence about the judge's decision, not provenance for a PRD claim. Forge should never turn a DeepEval, Ragas, or Promptfoo reason into credited PRD evidence. [Forge evidence rule](../../docs/SCORING_THEORY.md#evidence-rule); [G-Eval source](https://github.com/confident-ai/deepeval/blob/main/deepeval/metrics/g_eval/g_eval.py)

### Gaps

- Installed package sizes, dependency vulnerability counts, cold-start latency, and memory usage were not measured.
- DeepEval's TypeScript packaging and feature parity were not evaluated because Forge's relevant integration surface is Python and the recommendation is offline-only.
- The upstream docs do not promise immutable result schemas across the reviewed versions; any benchmark adapter should pin versions and validate imported/exported schemas.
- No legal review was performed; the license classifications report upstream files, not legal advice.

## What should Forge implement or benchmark next?

### Takeaway

Run one bounded Promptfoo spike and one smaller DeepEval G-Eval benchmark, both outside MCP/core and both against frozen Forge outputs plus independent labels. Do not add Ragas or DAGMetric dependencies. Keep pytest, `forge-calibration`, and `forge-review-eval` authoritative unless an external harness demonstrably improves orchestration without changing labels, evidence rules, or scoring. [Forge offline calibration](../../docs/ARCHITECTURE.md#offline-calibration); [Promptfoo CLI](https://www.promptfoo.dev/docs/usage/command-line/); [G-Eval docs](https://deepeval.com/docs/metrics-llm-evals)

### Cited Findings

#### Promptfoo benchmark plan

1. Pin Promptfoo 0.123.1 in a separate dev tool definition or container; do not add it to Forge's Python package metadata. Its official package requires Node `>=22.22.0` and includes direct provider SDKs. [Promptfoo release](https://github.com/promptfoo/promptfoo/releases/tag/0.123.1); [package metadata](https://github.com/promptfoo/promptfoo/blob/main/package.json)
2. Start with frozen Forge JSON using `--model-outputs` or a custom script provider. This avoids giving Promptfoo provider credentials and isolates whether the assertion/reporting layer adds value. [Promptfoo CLI](https://www.promptfoo.dev/docs/usage/command-line/); [custom script provider](https://www.promptfoo.dev/docs/providers/custom-script/)
3. Encode only outer invariants in Promptfoo: valid schema, expected band/verdict, unsupported quote rejection, prompt-injection fixture behavior, stable score under reordered sections, and expected deep-review finding IDs or Forge-computed metrics. Use Python assertions to call existing Forge validators rather than reimplementing rubric rules in YAML. [Python assertions](https://www.promptfoo.dev/docs/configuration/expected-outputs/python/); [Forge regression corpus](../../docs/SCORING_THEORY.md#regression-corpus)
4. For model/client variance, run uncached repeats, record exact model/client metadata, and preserve each run rather than averaging model outputs into a label. Promptfoo supports `--repeat`, `--no-cache`, tags, JSON/JUnit output, and CI failure codes. [Promptfoo CLI](https://www.promptfoo.dev/docs/usage/command-line/); [caching](https://www.promptfoo.dev/docs/configuration/caching/)
5. Disable Promptfoo telemetry and update checks, set an isolated config/cache directory, and inspect exports before sharing because they can contain prompts, outputs, variables, traces, and media. [Telemetry](https://www.promptfoo.dev/docs/configuration/telemetry/); [CLI environment and export](https://www.promptfoo.dev/docs/usage/command-line/)
6. Adopt Promptfoo only if the spike reduces matrix/CI/report maintenance while reproducing all existing Forge evaluator results exactly. Promptfoo must not calculate human consensus, calibration eligibility, source-span matching, criterion verdicts, weights, gates, or readiness bands. [Forge offline calibration](../../docs/ARCHITECTURE.md#offline-calibration)

#### DeepEval G-Eval benchmark plan

1. Pin released DeepEval 4.2.4 in an isolated optional benchmark environment; do not use unpinned `main`, which declared 4.2.6 on the audit date. [DeepEval release](https://github.com/confident-ai/deepeval/releases/tag/python-v4.2.4); [`main` metadata](https://github.com/confident-ai/deepeval/blob/main/pyproject.toml)
2. Test one narrow criterion at a time, such as whether a Forge deep-review finding clearly states the downstream consequence and required author decision. G-Eval is designed for subjective, use-case-specific criteria and supports explicit evaluation steps and score rubrics. [G-Eval docs](https://deepeval.com/docs/metrics-llm-evals)
3. Supply explicit evaluation steps rather than allowing G-Eval to regenerate them, pin the judge model and prompt/template, run repeated uncached evaluations, and report judge agreement separately from Forge stability. DeepEval says explicit steps improve controllability but still states that G-Eval is non-deterministic. [G-Eval calculation and FAQ](https://deepeval.com/docs/metrics-llm-evals#how-is-it-calculated)
4. Compare G-Eval results only against blinded human labels. Do not use G-Eval scores to tune readiness weights, gates, bands, or headline deep-review accuracy. Forge requires representative independent human labels for those claims. [Forge validation plan](../../docs/SCORING_THEORY.md#validation-plan); [D-024](../../docs/DECISIONS.md#d-024-calibrate-only-against-independent-human-labels)
5. Stop if the judge adds no information beyond existing labels, shows unacceptable model sensitivity, or cannot cite the exact frozen source evidence used in the case. DeepEval reasons are not mechanically source-bound. [G-Eval source](https://github.com/confident-ai/deepeval/blob/main/deepeval/metrics/g_eval/g_eval.py); [Forge evidence rule](../../docs/SCORING_THEORY.md#evidence-rule)

#### Ideas to borrow without dependencies

- From DAGMetric: show the executed decision path and distinguish model-selected branch decisions from fixed terminal score mappings. Forge should continue to label model classifications as classified/advisory and deterministic checks as proven. [DAG docs](https://deepeval.com/docs/metrics-dag); [Forge output restraint](../../docs/SCORING_THEORY.md#output-restraint)
- From Ragas: keep metrics single-aspect, interpretable, aligned against independent labels, and explicitly distinguish LLM-based from deterministic metrics. Forge's separate readiness calibration and deep-review evaluation already follow this separation and should retain it. [Ragas metric design principles](https://docs.ragas.io/en/stable/concepts/metrics/overview/); [Forge offline calibration](../../docs/ARCHITECTURE.md#offline-calibration)
- From Promptfoo: keep test cases declarative, support frozen outputs, make cache/repeat behavior explicit, emit machine-readable CI artifacts, and allow a provider/process adapter around the system under test. These are harness features, not scoring semantics. [Promptfoo CLI](https://www.promptfoo.dev/docs/usage/command-line/); [custom provider](https://www.promptfoo.dev/docs/providers/custom-api/); [caching](https://www.promptfoo.dev/docs/configuration/caching/)

#### Explicit non-adoption rules

- Do not place DeepEval, Ragas, Promptfoo, OpenAI, Anthropic, TypeSafe, LangChain, or other provider SDKs in Forge MCP/core dependencies as a result of this audit. [Forge D-006](../../docs/DECISIONS.md#d-006-client-llm-only); [Forge architecture](../../docs/ARCHITECTURE.md#boundary)
- Do not let G-Eval, DAGMetric, a Ragas LLM metric, Promptfoo `llm-rubric`, or Promptfoo G-Eval assign Forge readiness points, gates, bands, or evidence credit. [Forge scoring authority](../../docs/ARCHITECTURE.md#trust-boundaries); [DeepEval G-Eval](https://deepeval.com/docs/metrics-llm-evals); [Promptfoo LLM rubric](https://www.promptfoo.dev/docs/configuration/expected-outputs/model-graded/llm-rubric/)
- Do not report an LLM judge's agreement with Forge as human agreement or calibration. Public/synthetic/model labels remain diagnostics until independent human review exists. [Forge expert baseline](../../docs/SCORING_THEORY.md#expert-baseline); [validation plan](../../docs/SCORING_THEORY.md#validation-plan)
- Do not duplicate Forge's exact quote verification or rubric in an external framework configuration. Call Forge's existing validator/scorer and compare its structured output to independent expectations. [Forge evidence rule](../../docs/SCORING_THEORY.md#evidence-rule); [Forge architecture](../../docs/ARCHITECTURE.md#offline-calibration)

### Inferences

- Promptfoo has the highest expected value because it can remain completely outside the product runtime and exercise both deterministic outputs and model/client matrices. Its adoption threshold should nevertheless be high because Forge already has pytest, authored fixtures, calibration, review evaluation, and proxy diagnostics. [Promptfoo CLI](https://www.promptfoo.dev/docs/usage/command-line/); [Forge offline calibration](../../docs/ARCHITECTURE.md#offline-calibration)
- DeepEval G-Eval has research value only where human judgement is genuinely qualitative. Using it to grade exact schema, quote presence, or known labels would replace a cheap deterministic oracle with an expensive variable one. [G-Eval docs](https://deepeval.com/docs/metrics-llm-evals); [Forge evidence rule](../../docs/SCORING_THEORY.md#evidence-rule)
- Ragas would be reasonable for a product whose primary object is RAG answer quality, retrieval context, or citation accuracy. Forge's primary object is a source document plus a versioned readiness and deep-review contract, so adopting Ragas would force the problem into the wrong schema. [Ragas sample schema](https://docs.ragas.io/en/stable/references/evaluation_schema/); [Forge product purpose](../../docs/PRODUCT.md#purpose)
- If Promptfoo is eventually adopted, the clean architecture is `promptfoo process -> Forge CLI/script/MCP adapter -> structured Forge result -> deterministic/custom assertions`; model-graded assertions remain optional, separately reported, and never feed product scoring. [Promptfoo custom script provider](https://www.promptfoo.dev/docs/providers/custom-script/); [Forge portability](../../docs/ARCHITECTURE.md#portability)

### Gaps

- Acceptance thresholds for a Promptfoo spike have not been preregistered. At minimum they should cover exact parity with current fixture outcomes, setup/maintenance cost, runtime overhead, hermetic operation, and usefulness of generated reports.
- No independent human labels currently justify a headline G-Eval comparison for finding actionability; the existing proxy labels remain calibration-ineligible. [Forge validation plan](../../docs/SCORING_THEORY.md#validation-plan)
- Cross-client execution through Promptfoo, especially MCP-host behavior versus direct script invocation, needs an explicit fixture because Forge's client-borrowed sampling and agent fallback are different inference paths. [Forge inference modes](../../docs/ARCHITECTURE.md#inference-modes)
- Provider terms, data residency, and model retention policies are outside these framework repositories and must be reviewed separately before sending real internal PRDs to any hosted judge.
