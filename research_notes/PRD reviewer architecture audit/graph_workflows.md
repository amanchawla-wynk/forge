# Graph Retrieval and Workflow Orchestration for Forge

Research snapshot: 2026-09-25. All linked sources were accessed on 2026-09-25. Version observations refer to the upstream files and releases visible on that date: Microsoft GraphRAG 3.2.0, Neo4j GraphRAG for Python 1.21.0, and LangGraph 1.2.12. This audit evaluates Forge's current single-PRD review and remediation scope, not a hypothetical multi-document knowledge product.

## What do GraphRAG projects require and solve versus structured relational records plus criterion retrieval?

### Takeaway

Microsoft GraphRAG and Neo4j GraphRAG solve retrieval and answer generation over indexed corpora. Forge instead needs exhaustive evidence eligibility, exact-quote verification, deterministic joins among a bounded set of PRD facts, and conservative conflict detection. For the named V1 use cases, structured records plus Forge's in-memory graph are a better fit; retrieval ranking must not become an absence or completeness test.

#### Why retrieval is not the completeness mechanism

- Forge requires every normalized source block to participate in extraction; relevance-ranked retrieval cannot decide which PRD passages are eligible for credit. A claimed field receives no credit unless its quote is mechanically found in the normalized source. [Forge scoring theory](../../docs/SCORING_THEORY.md#evidence-rule)
- Microsoft GraphRAG's default outputs preserve raw text units and IDs, but entity descriptions, relationship descriptions and weights, community reports, rankings, and findings are LM-derived. The documented schema does not provide Forge's mandatory page/section/character span plus mechanical quote re-location contract. [Microsoft GraphRAG outputs](https://microsoft.github.io/graphrag/index/outputs/)
- Neo4j's retrievers return indexed or Cypher-derived context. Vector search is approximate nearest-neighbor retrieval, while `Text2CypherRetriever` uses an LLM to generate a query that is not guaranteed to be syntactically valid. These are useful query mechanisms, not proof that a required PRD fact is absent. [Neo4j RAG guide](https://neo4j.com/docs/neo4j-graphrag-python/current/user_guide_rag.html#vector-retriever); [Text2Cypher guide](https://neo4j.com/docs/neo4j-graphrag-python/current/user_guide_rag.html#text2cypher-retriever-user-guide)
- Microsoft GraphRAG can bring a user-supplied graph, but the query model remains RAG over graph/vector/community artifacts. Supplying Forge's already verified records would bypass most indexing value while retaining query-time machinery Forge does not need. [Microsoft GraphRAG custom graphs](https://microsoft.github.io/graphrag/index/byog/); [query overview](https://microsoft.github.io/graphrag/query/overview/)

#### Storage and query implications

- Microsoft GraphRAG writes its default index tables as Parquet files; its documented output model includes communities, community reports, covariates, documents, entities, relationships, and text units. [Microsoft GraphRAG outputs](https://microsoft.github.io/graphrag/index/outputs/)
- Microsoft GraphRAG supports LanceDB locally and Azure AI Search or Azure Cosmos DB as vector backends, with custom vector stores possible. [GraphRAG vectors README](https://github.com/microsoft/graphrag/tree/main/packages/graphrag-vectors)
- Neo4j GraphRAG is tied to a Neo4j graph database even when embeddings are generated locally; external vector stores such as Weaviate, Pinecone, and Qdrant are optional additional services. [Neo4j RAG guide](https://neo4j.com/docs/neo4j-graphrag-python/current/user_guide_rag.html#vector-databases-section)
- Forge's implemented requirement graph is a pair of typed Pydantic lists, rebuilt in process from verified claims. An executable spike stored the same 100-node/99-edge shape in an external property graph without improving exact evidence verification, leading D-050 to defer property-graph adoption. [Forge graph implementation](../../src/forge/deep_review.py); [comparison spike](../../spikes/graph_framework_comparison.py); [D-050](../../docs/DECISIONS.md#d-050-complete-the-deterministic-core-extend-the-taxonomy-and-defer-both-frameworks)

### Inferences

- The correct V1 retrieval unit is a criterion or verified claim selected by deterministic identity, not a semantically similar chunk. Criterion retrieval is sufficient for remediation because Forge already knows the exact failed criterion and target field. [Forge scoring theory](../../docs/SCORING_THEORY.md#remediation)
- The missing implementation work is domain modeling, not graph retrieval: stable goal, requirement, dependency, fallback, and test identities; source-unit reconstruction; and deterministic joins. Neither GraphRAG implementation removes that work. [Forge roadmap](../../docs/ROADMAP.md#current-build); [Microsoft GraphRAG overview](https://microsoft.github.io/graphrag/); [Neo4j RAG guide](https://neo4j.com/docs/neo4j-graphrag-python/current/user_guide_rag.html)
- A graph database becomes plausible only if Forge later needs a cross-document portfolio graph, independent concurrent graph queries, long-lived shared entities, user-authored Cypher, or graph sizes/traversals that exceed the bounded in-process model. None is in Forge's current product scope. [Forge product](../../docs/PRODUCT.md#initial-scope); [Forge architecture](../../docs/ARCHITECTURE.md#components)
- If semantic retrieval is ever benchmarked, it should be an advisory candidate-recall aid over already verified claims. It must be evaluated against blinded conflict labels and cannot decide absence, evidence eligibility, severity, or scoring. [D-047](../../docs/DECISIONS.md#d-047-validate-deep-review-with-blinded-finding-labels); [Forge scoring theory](../../docs/SCORING_THEORY.md#evidence-rule)

### Gaps

- Neither Microsoft nor Neo4j publishes a first-party benchmark for goals-without-metrics, requirements-without-goals, dependency fallback coverage, or contradiction precision/recall on PRDs.
- No reviewed upstream documentation promises exhaustive source-block eligibility and exact quote re-verification equivalent to Forge's contract.
- Forge has not yet measured representative graph node/edge counts across a labelled internal PRD set; the current external-store spike used a synthetic 100-node chain. [Comparison spike](../../spikes/graph_framework_comparison.py)
- Forge's implemented graph is narrower than its architecture target: actors, requirements, goals, dependencies, states, rollout rules, tests, and sections are not yet first-class graph nodes. [Forge architecture](../../docs/ARCHITECTURE.md#components); [Forge graph implementation](../../src/forge/deep_review.py)

## What model, embedding, provider, storage, license, runtime, and deployment costs exist?

### Takeaway

Both GraphRAG choices add model/storage boundaries that Forge's core deliberately avoids. Microsoft GraphRAG adds completion and embedding calls, a sizeable indexing stack, persisted index artifacts, and potentially managed vector services. Neo4j GraphRAG adds a Neo4j service plus provider-specific LLM/embedding extras for normal KG/RAG use. LangGraph's open-source runtime does not require a model provider, but durable checkpointers and production/background-job deployment add packages and, for managed or standalone Agent Server, infrastructure or commercial services.

#### Indexing and runtime cost specifics

- Standard Microsoft GraphRAG uses LLM calls for entity extraction, relationship extraction, entity summarization, relationship summarization, optional claims, and community reports. Microsoft estimates graph extraction at roughly 75% of indexing cost. [Microsoft index methods](https://microsoft.github.io/graphrag/index/methods/)
- FastGraphRAG replaces most extraction with NLTK/spaCy noun phrases and co-occurrence edges, but still uses an LLM for community reports; Microsoft says the resulting graph is noisier and positions it mainly for global summary questions. [Microsoft index methods](https://microsoft.github.io/graphrag/index/methods/)
- Microsoft GraphRAG warns that non-OpenAI models routed through LiteLLM or proxies must reliably produce its expected structured formats and that malformed JSON is a recurring issue. This conflicts with Forge's desire not to own provider/model compatibility in core. [GraphRAG model selection](https://microsoft.github.io/graphrag/config/models/); [Forge architecture](../../docs/ARCHITECTURE.md#inference-modes)
- Neo4j can use local Ollama and sentence-transformer embeddings, so provider fees are avoidable, but the database process, model runtime, embedding generation, index build, and operations remain. [Neo4j README](https://github.com/neo4j/neo4j-graphrag-python); [Neo4j RAG guide](https://neo4j.com/docs/neo4j-graphrag-python/current/user_guide_rag.html#embedders)
- Neo4j's KG construction namespace is explicitly experimental and may change or be removed; adopting it for Forge's core extraction would add stability risk on top of a mismatched evidence model. [Neo4j README](https://github.com/neo4j/neo4j-graphrag-python#-experimental-namespace)
- LangGraph writes a full state snapshot at each super-step by default. `DeltaChannel` can reduce append-heavy checkpoint size, but it is beta and depends on retaining/reconstructing ancestor writes. [LangGraph checkpointers](https://docs.langchain.com/oss/python/langgraph/checkpointers#optimize-checkpoint-storage)

### Inferences

- Microsoft GraphRAG is not merely a graph library. Even local use adds an indexing lifecycle, completion/embedding configuration, generated artifacts, prompt tuning, version migration, and a dependency stack larger than Forge's bounded analysis need. [GraphRAG overview](https://microsoft.github.io/graphrag/); [GraphRAG package metadata](https://github.com/microsoft/graphrag/blob/main/packages/graphrag/pyproject.toml)
- Neo4j retrieval without answer generation can omit an LLM when the caller supplies a query vector or deterministic Cypher, but Forge would then be paying the database/service cost only to execute joins already cheap in memory. [Neo4j RAG guide](https://neo4j.com/docs/neo4j-graphrag-python/current/user_guide_rag.html#vector-retriever-user-guide); [Forge comparison spike](../../spikes/graph_framework_comparison.py)
- LangGraph is the only evaluated option that can add functionality without changing Forge's model-provider boundary. Its real adoption cost is workflow/schema migration, extra checkpoint state, side-effect discipline, and possibly deployment infrastructure, not mandatory LLM or embedding fees. [LangGraph checkpointers](https://docs.langchain.com/oss/python/langgraph/checkpointers); [LangGraph interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)
- The lowest-cost V1 path remains Forge's current architecture: improve typed records and deterministic candidate recall before purchasing more retrieval or orchestration capability. [D-050](../../docs/DECISIONS.md#d-050-complete-the-deterministic-core-extend-the-taxonomy-and-defer-both-frameworks); [D-051](../../docs/DECISIONS.md#d-051-measure-deep-review-recall-before-adding-more-detectors)

### Gaps

- Upstream projects do not publish an end-to-end dollar cost for a representative Forge PRD. Provider, region, model, document size, retry, and deployment choices vary; no dollar estimate is defensible without a Forge-controlled benchmark.
- Cold-start time, installed size, memory, index latency, and transitive vulnerability surface have not been benchmarked in Forge for Microsoft GraphRAG 3.2.0 or Neo4j GraphRAG 1.21.0.
- LangSmith pricing and Neo4j Aura/Enterprise pricing are commercial and plan-dependent; the official sources establish plan/infrastructure requirements, not a stable workload price.
- Data-governance review would be required before sending PRD content, graph state, prompts, or traces to any managed vector, graph, model, or observability service.

## What does LangGraph add over Forge's optimistic-versioned SQLite sessions and idempotent operations?

### Takeaway

LangGraph adds a general durable execution engine: graph topology, parallel super-steps, persisted node writes, resumable interrupts, retries, replay/forking, state history, and deployable background runtime options. Forge already has the narrower product behavior it currently needs: durable resume, one-user HITL, explicit legal transitions, optimistic concurrency, request-bound idempotency, operation reservation, and semantic audit. LangGraph becomes warranted only when durable branching, independent parallel work with partial-failure recovery, long-running background execution, or multi-party approvals are concrete requirements.

#### What LangGraph does not replace

- Forge's `session_version` is a caller-visible compare-and-swap token for one authoritative review head. LangGraph checkpoint IDs identify historical snapshots and may have forks; the official checkpointer interface does not document an equivalent expected-version precondition for an external mutation. [Forge sessions](../../src/forge/sessions.py); [LangGraph checkpointer interface](https://docs.langchain.com/oss/python/langgraph/checkpointers#checkpointer-interface)
- Forge's `operation_id` is stable across caller retries and bound to operation type plus request digest. The official LangGraph checkpointer contract stores checkpoints and task writes; it does not document an equivalent request-digest operation ledger or an atomic transaction spanning Forge session, operation, and semantic-event records. [Forge sessions](../../src/forge/sessions.py); [LangGraph checkpointer interface](https://docs.langchain.com/oss/python/langgraph/checkpointers#checkpointer-interface)
- Resuming a LangGraph interrupt restarts its node from the beginning. The official guidance requires effects before an interrupt to be idempotent or separated into another node. [LangGraph interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts#rules-of-interrupts)
- Replay re-executes downstream LLM calls, API requests, and interrupts. `update_state` creates a new checkpoint rather than mutating the original, and reducers may accumulate rather than overwrite values. [LangGraph checkpointers](https://docs.langchain.com/oss/python/langgraph/checkpointers#replay); [time travel](https://docs.langchain.com/oss/python/langgraph/use-time-travel)
- LangGraph checkpointers store execution snapshots; Forge still must own exact source/rubric/workspace/user binding, review discovery, cross-client confirmation, TTL, deletion policy, legal workflow transitions, evidence verification, and scoring. [Forge sessions](../../src/forge/sessions.py); [D-042](../../docs/DECISIONS.md#d-042-forge-owns-review-identity-and-new-chats-resume-explicit)

#### Evidence from the existing spike

- Forge's 2026-09-25 executable spike used LangGraph 1.0.8 with SQLite. It demonstrated `interrupt`, `Command(resume=...)`, three checkpoints, and mapping `thread_id` to a Forge review ID. It recorded no native operation-digest guard and no native source/rubric/workspace binding. [Forge comparison spike](../../spikes/graph_framework_comparison.py); [D-050](../../docs/DECISIONS.md#d-050-complete-the-deterministic-core-extend-the-taxonomy-and-defer-both-frameworks)
- LangGraph 1.2.12 was the current release visible on 2026-09-25; the current docs add richer event streaming, multiple interrupt resume by ID, checkpointer conformance, optional encryption, durability modes, and beta delta channels. These improve runtime capability but do not introduce the missing Forge domain guards described above. [LangGraph releases](https://github.com/langchain-ai/langgraph/releases); [interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts); [checkpointers](https://docs.langchain.com/oss/python/langgraph/checkpointers)

### Inferences

- LangGraph would currently duplicate rather than replace persistence unless Forge either keeps two authorities or writes a custom saver/transaction envelope. The first creates divergence risk; the second retains most hard repository work. [LangGraph custom checkpointer](https://docs.langchain.com/oss/python/langgraph/checkpointers#build-a-custom-checkpointer); [Forge sessions](../../src/forge/sessions.py)
- The strongest future LangGraph use is orchestration without LangChain agents: `thread_id = review_session_id`, Forge domain models remain graph state, each expensive side effect is an isolated node behind Forge's reservation ledger, and Forge DTOs/`next_action` remain the public MCP contract. [Forge architecture](../../docs/ARCHITECTURE.md#mcp-tool-direction); [D-050](../../docs/DECISIONS.md#d-050-complete-the-deterministic-core-extend-the-taxonomy-and-defer-both-frameworks)
- Durable branching is not currently a benefit because Forge deliberately prevents implicit session merging and gives parallel reviews separate identities. It becomes a benefit only when product requirements define branch ownership, comparison, merge/selection, and audit behavior. [Forge product](../../docs/PRODUCT.md#continuing-in-a-new-chat-or-client); [D-042](../../docs/DECISIONS.md#d-042-forge-owns-review-identity-and-new-chats-resume-explicit)
- Existing HITL is sufficient because the current interaction is one user, one question, one queue, and bounded checkpoints. Multi-party approvals with independently durable pending decisions would change that conclusion. [Forge scoring theory](../../docs/SCORING_THEORY.md#remediation); [LangGraph interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts#handling-multiple-interrupts)
- Background jobs would justify a new evaluation only if Forge itself becomes responsible for long-running multi-batch/model work after the initiating MCP call returns. A managed Agent Server decision must remain separate from adopting the OSS graph library. [LangSmith deployment](https://docs.langchain.com/langsmith/deployment); [Forge architecture](../../docs/ARCHITECTURE.md#inference-modes)

### Gaps

- Forge has not stress-tested LangGraph 1.2.12 and `langgraph-checkpoint-sqlite` 3.1.1 for concurrent invocations on one thread, stale external versions, request-bound idempotency, crash points around model calls, or Forge-sized state growth.
- The official docs reviewed do not establish a transaction that atomically commits a LangGraph checkpoint plus Forge's session head, operation result, and semantic event.
- No concrete Forge requirement currently defines background execution, durable branch merge/selection, or multi-party approval roles. Without that product contract, a framework benchmark would optimize hypothetical behavior.
- MCP sampling's future replacement remains unresolved in Forge's roadmap. Orchestrating provider calls inside Forge before that boundary is settled could benchmark the wrong execution model. [Forge roadmap](../../docs/ROADMAP.md#next)

## Which options should Forge adopt, benchmark, borrow from, or reject now?

### Takeaway

Do not add either GraphRAG implementation or LangGraph to V1 production dependencies. Classify Microsoft GraphRAG and Neo4j GraphRAG as **NOT NEEDED** for the current product. Classify LangGraph as **BORROW IDEAS**: retain its node-boundary, interrupt, pending-write, durability, and replay-safety patterns, but do not run another benchmark until a concrete adoption trigger exists.

### Cited Findings

| Option | Classification now | Decision rationale | Revisit trigger |
|---|---|---|---|
| Microsoft GraphRAG 3.2.0 | **NOT NEEDED** | Its core value is graph-enhanced RAG over private corpora using LM-extracted entities/relations, Leiden communities, generated reports, embeddings, and query-time context construction. Forge requires exhaustive field extraction and exact source verification, and its architecture explicitly says the bounded graph needs neither embeddings nor communities. [Microsoft GraphRAG overview](https://microsoft.github.io/graphrag/); [Forge architecture](../../docs/ARCHITECTURE.md#components) | A separately scoped multi-document research/portfolio product with holistic questions, repeated corpus queries, and a benchmark showing global/local/DRIFT retrieval outperforms simpler retrieval while preserving citation requirements. |
| Neo4j GraphRAG for Python 1.21.0 | **NOT NEEDED** | It is a capable Neo4j retrieval/generation toolkit, but requires a database and usually indexes/embeddings/LLMs for features Forge does not need. A database can persist Forge's bounded graph but adds no conflict or completeness semantics. [Neo4j README](https://github.com/neo4j/neo4j-graphrag-python); [Neo4j RAG guide](https://neo4j.com/docs/neo4j-graphrag-python/current/user_guide_rag.html); [D-050](../../docs/DECISIONS.md#d-050-complete-the-deterministic-core-extend-the-taxonomy-and-defer-both-frameworks) | Cross-document/shared graph persistence, concurrent graph query workloads, Cypher as a product capability, or measured in-memory scale/latency failure. Benchmark storage only with the same verified claims and no default LLM extraction. |
| LangGraph 1.2.12 | **BORROW IDEAS** | Its durable execution, interrupts, pending writes, replay, branching, and deployment runtime are real additions, but Forge already covers present resume/HITL needs and has stronger product-specific concurrency/idempotency guards. D-050 already ran an executable spike and deferred adoption until durable branching, background work, or multi-party approvals become real. [LangGraph checkpointers](https://docs.langchain.com/oss/python/langgraph/checkpointers); [LangGraph interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts); [D-050](../../docs/DECISIONS.md#d-050-complete-the-deterministic-core-extend-the-taxonomy-and-defer-both-frameworks) | At least one concrete requirement for durable fan-out with partial-failure recovery, process-independent background runs, branch selection/merge, or several independent approvers. Then classify a new spike as **BENCHMARK**, not automatic adoption. |
| Forge bounded graph + SQLite workflow | **ADOPT** | Already implemented, aligned with local-first/provider-independent boundaries, exact provenance, deterministic scoring, optimistic concurrency, request-digest idempotency, and current one-user remediation. [Forge architecture](../../docs/ARCHITECTURE.md); [Forge sessions](../../src/forge/sessions.py); [D-050](../../docs/DECISIONS.md#d-050-complete-the-deterministic-core-extend-the-taxonomy-and-defer-both-frameworks) | Continue only while measured graph/workflow size, latency, failure recovery, and maintenance remain acceptable. |

#### Ideas worth borrowing without dependencies

- From Microsoft GraphRAG: keep query intent explicit. Distinguish corpus-level summaries, entity-local questions, and ordinary top-k retrieval rather than calling every graph operation GraphRAG. Forge's current use cases are structured validation and one/two-hop consistency, not global search. [Microsoft GraphRAG overview](https://microsoft.github.io/graphrag/)
- From Neo4j GraphRAG: separate retrieval from generation and make retrieval strategies explicit. A deterministic record/Cypher-like query should remain callable without an LLM, and generated answers should expose retrieved context. [Neo4j RAG guide](https://neo4j.com/docs/neo4j-graphrag-python/current/user_guide_rag.html#graph-rag-search-options)
- From LangGraph: isolate side effects into idempotent nodes, place human interrupts before mutations, retain stable interrupt identities, distinguish execution history from semantic audit, and design crash tests at every expensive boundary. [LangGraph interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts#rules-of-interrupts); [LangGraph checkpointers](https://docs.langchain.com/oss/python/langgraph/checkpointers)
- From LangGraph: preserve successful results from independent parallel work rather than rerunning them after a sibling failure. Forge can implement this with its existing plan/run fingerprints and operation ledger before needing a graph runtime. [LangGraph pending writes](https://docs.langchain.com/oss/python/langgraph/checkpointers#pending-writes); [D-043](../../docs/DECISIONS.md#d-043-harden-durable-review-integrity-before-expanding-scope)

#### Decision gates for any future benchmark

- A GraphRAG benchmark must use representative labelled PRDs and compare candidate/finding recall, false positives, exact quote alignment, token use, latency, index size, and cold start against criterion retrieval plus Forge's bounded graph. It must not use GraphRAG output as its own ground truth. [D-047](../../docs/DECISIONS.md#d-047-validate-deep-review-with-blinded-finding-labels)
- A Neo4j benchmark must ingest the same already verified claim/edge records, disable default KG extraction, and prove value in query latency, concurrent access, or code deletion. Merely reproducing the same nodes and edges is a failed adoption case. [Comparison spike](../../spikes/graph_framework_comparison.py)
- A LangGraph benchmark must retain `review_session_id`, external `session_version`, operation type/request digest binding, one authoritative head, ownership checks, semantic events, source/rubric fingerprints, and no-overwrite revision behavior. It must pass Forge's existing restart, stale-version, duplicate-operation, wrong-document, parallel-review, and cross-client-resume tests. [Forge sessions](../../src/forge/sessions.py); [Forge roadmap](../../docs/ROADMAP.md#completed)
- Adoption requires measured net simplification after counting adapter code, schema migration, persisted-checkpoint compatibility, custom transaction/idempotency integration, deployment, and operations. Feature-list overlap is not sufficient. [D-040](../../docs/DECISIONS.md#d-040-checkpoint-remediation-and-extract-only-answer-deltas); [D-050](../../docs/DECISIONS.md#d-050-complete-the-deterministic-core-extend-the-taxonomy-and-defer-both-frameworks)

### Inferences

- The immediate architecture decision is stable: improve Forge's source-unit reconstruction and typed requirement/dependency relations before evaluating retrieval or workflow frameworks. The measured bottleneck is claim granularity and recall, not graph storage or pause/resume. [D-051](../../docs/DECISIONS.md#d-051-measure-deep-review-recall-before-adding-more-detectors); [Forge roadmap](../../docs/ROADMAP.md#current-build)
- “Avoid GraphRAG for V1 absent a concrete need” is not merely a simplicity preference. It protects exhaustive evidence coverage, provider independence, local deployment, and deterministic scoring from a retrieval stack whose generated summaries and ranked context are not authoritative. [Forge scoring theory](../../docs/SCORING_THEORY.md#evidence-rule); [Microsoft GraphRAG outputs](https://microsoft.github.io/graphrag/index/outputs/)
- “Avoid LangGraph merely because LLMs are involved” follows from the workflow shape. LLM calls are bounded extraction/classification steps inside a mostly deterministic, already durable state machine; model presence does not itself create a need for general orchestration. [Forge architecture](../../docs/ARCHITECTURE.md#inference-modes); [D-040](../../docs/DECISIONS.md#d-040-checkpoint-remediation-and-extract-only-answer-deltas)
- If future requirements cross the trigger, the likely architecture is Forge domain core plus Forge identity/idempotency envelope plus LangGraph orchestration, not a rewrite as a LangChain agent and not replacement of Forge evidence/scoring authority. [Forge architecture](../../docs/ARCHITECTURE.md#mcp-tool-direction); [LangGraph checkpointers](https://docs.langchain.com/oss/python/langgraph/checkpointers)

### Gaps

- The classification is architecture-fit guidance, not an empirical claim that GraphRAG can never improve advisory conflict recall. That requires the benchmark and human-labelled corpus described above.
- Forge lacks independent human labels for current deep-review precision/recall, so its existing low proxy recall identifies a development bottleneck but cannot validate the final detector or compare production quality. [D-047](../../docs/DECISIONS.md#d-047-validate-deep-review-with-blinded-finding-labels); [D-051](../../docs/DECISIONS.md#d-051-measure-deep-review-recall-before-adding-more-detectors)
- The future value of background execution depends on MCP/client evolution and whether Forge assumes ownership of inference scheduling. Current OpenCode and Cursor fallback execution remains caller-orchestrated. [Forge architecture](../../docs/ARCHITECTURE.md#inference-modes); [D-044](../../docs/DECISIONS.md#d-044-treat-cursor-as-a-non-sampling-client)
