# MCP Integration Architecture Audit

## What official MCP facilities are current as of 2026-09-25, especially after sampling deprecation/SEP-2577?

### Takeaway
The current baseline is MCP specification `2026-07-28` and official Python SDK `2.2.0`. New Forge work should use ordinary client-to-server tools with structured outputs and treat multi-round-trip `InputRequiredResult` as an optional, capability-detected optimization; it should not build further on legacy server-initiated sampling. Forge's agent-driven prepare/submit workflow is the most portable inference boundary across Claude, ChatGPT, Gemini, and coding agents.

### Cited Findings
- The authoritative current protocol revision is `2026-07-28`. It defines tools, resources, and prompts as server features; elicitation as a client feature; and Tasks as an opt-in extension rather than a core feature. Accessed 2026-09-25. — [MCP specification 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28)
- The official MCP Python SDK's current stable line is v2, supporting the `2026-07-28` protocol and earlier revisions. `pip install mcp` now installs 2.x; v1 is maintained on a separate branch for critical/security fixes. Accessed 2026-09-25. — [Official Python SDK README](https://github.com/modelcontextprotocol/python-sdk/blob/main/README.md)
- The latest official Python SDK release is `v2.2.0`, published 2026-09-07, under the MIT license. Forge already declares `mcp>=2.2,<3`, so its dependency range is on the correct major/current minimum. Accessed 2026-09-25. — [Python SDK v2.2.0 release](https://github.com/modelcontextprotocol/python-sdk/releases/tag/v2.2.0); [SDK repository license](https://github.com/modelcontextprotocol/python-sdk/blob/main/LICENSE)
- SEP-2577 finalized deprecation of Roots, Sampling, and protocol Logging because of low adoption relative to implementation complexity. The proposal states that the deprecation is advisory for older specification versions and makes no wire-level change to those versions. Accessed 2026-09-25. — [SEP-2577](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2577)
- On a modern `2026-07-28` connection, standalone server-to-client `sampling/createMessage` has no back-channel and fails; it remains usable only on a negotiated pre-2026/legacy session. The SDK explicitly says new code should not be built on it. Accessed 2026-09-25. — [Python SDK deprecated features](https://py.sdk.modelcontextprotocol.io/deprecated/)
- The replacement is client-initiated multi-round-trip requests: a server returns `InputRequiredResult` containing `CreateMessageRequest`, `ElicitRequest`, or `ListRootsRequest`; the client fulfills the requests and retries the same operation with `inputResponses` and opaque `requestState`. The sampling payload survives, but server-initiated sampling does not. Accessed 2026-09-25. — [Python SDK multi-round-trip requests](https://py.sdk.modelcontextprotocol.io/handlers/multi-round-trip/)
- `InputRequiredResult` exists only in protocol `2026-07-28`; pre-2026 sessions cannot serialize it. High-level `MCPServer` seals request state by default, while multi-worker/restart-surviving remote deployments must provide shared request-state keys and bind state to authenticated identity. Accessed 2026-09-25. — [Python SDK multi-round-trip requests](https://py.sdk.modelcontextprotocol.io/handlers/multi-round-trip/)
- Elicitation now travels through `InputRequiredResult`. Form mode is limited to flat primitive schemas and must not collect passwords, API keys, access tokens, or payment credentials; URL mode is required for sensitive/out-of-band interactions. Accessed 2026-09-25. — [MCP elicitation specification](https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation)
- Tasks are an extension for durable asynchronous operations, polling, cancellation, progress, and `input_required` states. Client support is explicitly variable, and Python SDK `2.2.0` lists Tasks/SEP-2663 as not yet implemented. Accessed 2026-09-25. — [MCP Tasks extension overview](https://modelcontextprotocol.io/specification/2026-07-28/basic/utilities/tasks); [Python SDK v2.2.0 release](https://github.com/modelcontextprotocol/python-sdk/releases/tag/v2.2.0)
- The current Python SDK supports local stdio and remote Streamable HTTP. For HTTP authorization, the server is an OAuth 2.1 resource server that verifies tokens rather than issuing them. Accessed 2026-09-25. — [Python SDK README](https://github.com/modelcontextprotocol/python-sdk/blob/main/README.md); [Python SDK authorization](https://py.sdk.modelcontextprotocol.io/run/authorization/)
- Roots are deprecated; the SDK recommends ordinary tool arguments or resource URIs for paths. Resources are application-controlled context and prompts are user-invoked templates, whereas tools are model-controlled actions. Accessed 2026-09-25. — [Python SDK deprecated features](https://py.sdk.modelcontextprotocol.io/deprecated/); [MCP specification 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28)
- MCP's own current overview names Claude and ChatGPT plus coding environments such as VS Code and Cursor as broadly supported MCP hosts. Gemini CLI is separately listed by Atlassian as a supported MCP client, but support for individual protocol extensions still varies by host. Accessed 2026-09-25. — [MCP client overview](https://modelcontextprotocol.io/clients); [Atlassian MCP Server README](https://github.com/atlassian/atlassian-mcp-server/blob/main/README.md)

### Inferences
- **ADOPT:** Make the existing `prepare_*` -> host/agent inference -> `apply_*`/`score_*` contract Forge's normative model-independent boundary. It uses only universally composable tool calls and keeps model selection, credentials, and inference policy in the host; SEP-2577 confirms that relying on a client back-channel is not a durable portability strategy. — [SEP-2577](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2577); [Python SDK deprecated features](https://py.sdk.modelcontextprotocol.io/deprecated/)
- **ADOPT, optional:** Add a `2026-07-28` MRTR implementation only as a capability-negotiated convenience path that returns `InputRequiredResult(CreateMessageRequest)` and converges on the exact same verified Forge service operation as the fallback. Do not describe it as a replacement that all hosts support. — [Python SDK multi-round-trip requests](https://py.sdk.modelcontextprotocol.io/handlers/multi-round-trip/)
- **ADOPT:** Keep local paths as explicit tool arguments for trusted local/stdio use, and add a content/snapshot ingestion form for web and remote hosts that cannot dereference a user's local path. Do not replace explicit path validation with deprecated Roots. — [Python SDK deprecated features](https://py.sdk.modelcontextprotocol.io/deprecated/)
- **BORROW IDEAS:** Resources can expose immutable normalized blocks, visual assets, or review artifacts by URI for clients that use them well, and prompts can package an optional guided workflow. Neither should be required for assessment because tools have the strongest cross-host invocation semantics and Forge must validate all inputs itself. — [MCP specification 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28)
- **ADOPT:** Use elicitation only for small explicit choices or confirmations, such as Resume / Start new / Cancel or revision approval. Continue accepting ordinary tool arguments as the universal fallback; never use form elicitation for credentials. — [MCP elicitation specification](https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation)
- **BENCHMARK:** Tasks map well to long ingestion, full multi-batch review, final reassessment, and resumable checkpoints, but adoption should wait until the Python SDK implements SEP-2663 and target hosts demonstrate interoperable support. Forge's current durable SQLite review state should remain authoritative during any spike. — [MCP Tasks extension overview](https://modelcontextprotocol.io/specification/2026-07-28/basic/utilities/tasks); [Python SDK v2.2.0 release](https://github.com/modelcontextprotocol/python-sdk/releases/tag/v2.2.0)
- **NOT NEEDED:** Provider SDKs, provider API keys, or a model gateway in Forge MCP/core. MRTR still delegates model execution to the client, while the agent fallback already works when that facility is absent. — [Python SDK multi-round-trip requests](https://py.sdk.modelcontextprotocol.io/handlers/multi-round-trip/)
- **NOT NEEDED:** Server-to-server MCP orchestration inside Forge. MCP defines the host as the coordinator of client connections; composing Forge with source servers at the host avoids making Forge an MCP client, credential broker, and policy engine. — [MCP specification 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28)
- **ADOPT for any future remote Forge:** Streamable HTTP, OAuth resource-server verification, subject/tenant ownership checks, request-state integrity, and least-privilege scopes. Keep stdio/local mode credential-free. — [Python SDK authorization](https://py.sdk.modelcontextprotocol.io/run/authorization/); [Python SDK multi-round-trip requests](https://py.sdk.modelcontextprotocol.io/handlers/multi-round-trip/)

### Gaps
- No primary source establishes a uniform Claude, ChatGPT, Gemini, Cursor, OpenCode, and Copilot support matrix for `2026-07-28` MRTR, elicitation modes, or Tasks. Capability probing and a per-host conformance suite remain necessary. — [MCP Tasks extension overview](https://modelcontextprotocol.io/specification/2026-07-28/basic/utilities/tasks)
- The official SDK documentation explains migration mechanics but does not guarantee that hosts will expose model invocation through embedded `CreateMessageRequest`; Forge cannot retire its agent-driven fallback on specification availability alone. — [Python SDK multi-round-trip requests](https://py.sdk.modelcontextprotocol.io/handlers/multi-round-trip/)

## How invasive or portable are Docling MCP and Atlassian MCP integrations?

### Takeaway
Docling MCP is portable as a separately configured peer server but invasive as an embedded Forge dependency, especially in local/OCR/RAG modes. Atlassian MCP is intentionally a hosted peer integration: it is broad across major clients, but Cloud-only, OAuth/API-token dependent, and unsuitable as a library inside Forge.

### Cited Findings
- Docling MCP `3.2.1` was released 2026-09-24, uses MCP Python SDK `>=2,<3`, requires Python `>=3.10`, and is MIT licensed. Its base dependencies include `docling-slim[service-client]~=2.92` and `docling-core>=2.51.0`; local conversion adds `docling-slim[standard]~=2.92`. Accessed 2026-09-25. — [Docling MCP v3.2.1 release](https://github.com/docling-project/docling-mcp/releases/tag/v3.2.1); [Docling MCP pyproject](https://github.com/docling-project/docling-mcp/blob/main/pyproject.toml); [Docling MCP license](https://github.com/docling-project/docling-mcp/blob/main/LICENSE)
- Docling MCP exposes conversion and document-generation tools, accepts local files and URLs, can retain images, enables OCR and table structure by default, and caches converted documents in a bounded in-memory LRU. Accessed 2026-09-25. — [Docling MCP README](https://github.com/docling-project/docling-mcp/blob/main/README.md); [Docling MCP v3.2.1 release](https://github.com/docling-project/docling-mcp/releases/tag/v3.2.1)
- Docling MCP's recommended lightweight mode depends on a separate Docling Serve endpoint and API key; local mode requires the larger `local` extra; hybrid mode combines both. Optional RAG tool groups add LlamaIndex, Milvus, model/embedding endpoints, or LlamaStack. Accessed 2026-09-25. — [Docling MCP README](https://github.com/docling-project/docling-mcp/blob/main/README.md); [Docling MCP pyproject](https://github.com/docling-project/docling-mcp/blob/main/pyproject.toml)
- Docling MCP supports stdio, SSE, and Streamable HTTP and documents normal peer-server installation through client configuration. This makes it host-composable without importing its runtime into Forge. Accessed 2026-09-25. — [Docling MCP README](https://github.com/docling-project/docling-mcp/blob/main/README.md)
- The official Atlassian MCP Server is a cloud-hosted bridge, is generally available, uses the `https://mcp.atlassian.com/v2/mcp` endpoint, and is Apache-2.0 licensed. Its repository has no numbered GitHub release as of the access date; `v2` is the service endpoint generation, not a repository/package semantic version. Accessed 2026-09-25. — [Atlassian MCP Server README](https://github.com/atlassian/atlassian-mcp-server/blob/main/README.md); [Atlassian MCP Server license](https://github.com/atlassian/atlassian-mcp-server/blob/main/LICENSE)
- Atlassian officially documents compatibility with ChatGPT, Claude, Cursor, VS Code/Copilot, Codex, Gemini CLI, and other MCP clients. It also publishes Agent Plugin, Claude, Cursor, Gemini extension, and MCP Registry manifests. Accessed 2026-09-25. — [Atlassian MCP Server README](https://github.com/atlassian/atlassian-mcp-server/blob/main/README.md)
- Atlassian MCP supports Confluence read/write/search permission groups and enforces the signed-in user's existing permissions. OAuth 2.1 and API-token modes are available, with admin controls, audit logs, IP allowlists, and domain controls. Accessed 2026-09-25. — [Atlassian MCP Server README](https://github.com/atlassian/atlassian-mcp-server/blob/main/README.md)
- Atlassian says its MCP server does not store or cache Jira or Confluence content and acts as a secure proxy. It is available to Atlassian Cloud customers, but currently does not support FedRAMP or HIPAA requirements. Accessed 2026-09-25. — [Atlassian Rovo MCP product page](https://www.atlassian.com/platform/rovo-mcp)
- Atlassian's legacy SSE endpoint was scheduled to stop after 2026-06-30; current connections should use `/mcp`, preferably `/v2/mcp`. Accessed 2026-09-25. — [Atlassian MCP Server README](https://github.com/atlassian/atlassian-mcp-server/blob/main/README.md)

### Inferences
- **BENCHMARK:** Compare direct Docling library output against Forge's current PyMuPDF/python-docx normalization on representative PDFs and DOCX files. Measure reading order, heading/table recovery, OCR yield, stable page/section provenance, exact quote relocation, latency, memory, install size, and offline behavior. Docling's richer parse is useful only if Forge can map it deterministically into its own evidence blocks. — [Docling MCP README](https://github.com/docling-project/docling-mcp/blob/main/README.md); [Docling MCP pyproject](https://github.com/docling-project/docling-mcp/blob/main/pyproject.toml)
- **NOT NEEDED:** Do not embed `docling-mcp` itself in Forge. It duplicates the MCP server/runtime boundary and brings conversion modes, cache behavior, generation, and optional RAG/model concerns that Forge does not need. If the benchmark succeeds, depend on the narrow Docling parsing library behind a Forge-owned adapter, not its MCP wrapper. — [Docling MCP README](https://github.com/docling-project/docling-mcp/blob/main/README.md); [Docling MCP pyproject](https://github.com/docling-project/docling-mcp/blob/main/pyproject.toml)
- **BORROW IDEAS:** Retain Docling MCP's bounded cache, selectable local/remote conversion, OCR/table switches, and explicit image-export policy as design references. Forge should not borrow its RAG/model extras because those would violate Forge's provider-independent core boundary. — [Docling MCP README](https://github.com/docling-project/docling-mcp/blob/main/README.md)
- **ADOPT as peer:** Treat Atlassian MCP as the default Confluence access server. It already owns Atlassian Cloud API evolution, OAuth consent, scopes, admin policy, rate limits, and audit behavior across all target host families. — [Atlassian MCP Server README](https://github.com/atlassian/atlassian-mcp-server/blob/main/README.md)
- **NOT NEEDED:** Do not import or proxy the Atlassian MCP implementation inside Forge. It is a hosted service rather than an embeddable library, and absorbing its auth would make Forge responsible for credentials, tenant identity, product permissions, and cloud-specific operational policy. — [Atlassian MCP Server README](https://github.com/atlassian/atlassian-mcp-server/blob/main/README.md)
- **ADOPT:** Pin documentation and setup to Atlassian `/v2/mcp`, not legacy SSE or v1 endpoints. Treat Atlassian's service version independently from Forge's adapter/snapshot schema version. — [Atlassian MCP Server README](https://github.com/atlassian/atlassian-mcp-server/blob/main/README.md)

### Gaps
- Docling MCP's documentation does not establish evidence-grade fidelity for Forge's exact quote and source-location invariants. Only a fixture benchmark can answer whether Docling improves or destabilizes Forge normalization. — [Docling MCP README](https://github.com/docling-project/docling-mcp/blob/main/README.md)
- Atlassian's public repository does not publish a numbered software release corresponding to endpoint `v2`, so there is no package version Forge can pin; compatibility must be verified against the live service contract and Forge's own snapshot schema. — [Atlassian MCP Server repository](https://github.com/atlassian/atlassian-mcp-server)
- Atlassian Cloud-only support leaves Confluence Data Center and regulated deployments unresolved. A future direct adapter would need a separate product/security decision rather than being inferred from the cloud peer-server design. — [Atlassian Rovo MCP product page](https://www.atlassian.com/platform/rovo-mcp)

## Should Confluence ingestion live inside Forge, use Atlassian MCP as a peer, or support both through an adapter contract?

### Takeaway
Use Atlassian MCP as an upstream peer and support both local files and externally fetched content through a Forge-owned, source-neutral snapshot contract. Do not put Confluence authentication or API calls in Forge core; reserve an optional direct adapter for a demonstrated gap such as Data Center, unattended service ingestion, or evidence metadata unavailable from the peer workflow.

### Cited Findings
- Atlassian MCP already supplies Confluence search/read/write tools, OAuth/API-token authentication, user-permission enforcement, admin controls, and official integrations for Claude, ChatGPT, Gemini CLI, and coding agents. Accessed 2026-09-25. — [Atlassian MCP Server README](https://github.com/atlassian/atlassian-mcp-server/blob/main/README.md)
- Current MCP places the host between its clients and servers. Server-to-server composition is not required: a host/agent can call Atlassian, receive content, and invoke Forge with that content. Accessed 2026-09-25. — [MCP specification 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28)
- Current MCP deprecates Roots and recommends path arguments or resource URIs, while modern MRTR can carry input requests but remains version- and client-dependent. Accessed 2026-09-25. — [Python SDK deprecated features](https://py.sdk.modelcontextprotocol.io/deprecated/); [Python SDK multi-round-trip requests](https://py.sdk.modelcontextprotocol.io/handlers/multi-round-trip/)
- Atlassian warns that MCP clients and agents can be exposed to indirect prompt injection and tool poisoning and recommends trusted servers, least privilege, human confirmation for high-impact actions, and audit monitoring. Accessed 2026-09-25. — [Atlassian MCP Server README](https://github.com/atlassian/atlassian-mcp-server/blob/main/README.md)

### Inferences
- **ADOPT:** Define one Forge-owned ingestion/snapshot contract that can represent `local_file`, `inline_content`, and `external_snapshot` without making source acquisition part of scoring. At minimum it should carry immutable bytes/text, media type, source display name, canonical source URI when available, external revision/version and retrieval time when available, and adapter provenance. The normalized-document hash remains Forge's assessment identity. This preserves Forge's evidence boundary regardless of whether content came from a file tool, Atlassian peer, upload, or future adapter. — [MCP specification 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28); [Atlassian MCP Server README](https://github.com/atlassian/atlassian-mcp-server/blob/main/README.md)
- **ADOPT:** Recommended Confluence flow: the host authenticates to Atlassian MCP, searches/reads a page under the user's permissions, snapshots the returned page and provenance, then calls Forge's ingestion/review tools. Forge treats all page text as untrusted document data and never treats Atlassian tool metadata as scored PRD evidence unless it is deliberately normalized into the evidence corpus. — [Atlassian MCP Server README](https://github.com/atlassian/atlassian-mcp-server/blob/main/README.md)
- **ADOPT:** Keep source acquisition replaceable through an adapter protocol in the domain/service layer, but initially ship only local/inline/snapshot adapters. This supports future Confluence Data Center or direct REST acquisition without committing Forge core to Atlassian credentials today. — [Atlassian Rovo MCP product page](https://www.atlassian.com/platform/rovo-mcp)
- **BENCHMARK:** Test whether host-mediated Atlassian results preserve enough Confluence structure and revision metadata for deterministic evidence locations. If they do not, benchmark a separately packaged optional Atlassian adapter against the peer path before adding it. — [Atlassian MCP Server README](https://github.com/atlassian/atlassian-mcp-server/blob/main/README.md)
- **NOT NEEDED:** Forge should not automatically write review results back to Confluence. A host can compose Forge's approved revision artifact with Atlassian's write tools, preserving explicit user approval and keeping publishing credentials outside Forge. — [Atlassian MCP Server README](https://github.com/atlassian/atlassian-mcp-server/blob/main/README.md)
- **BORROW IDEAS:** Atlassian's permission-group separation and on-demand tool discovery are useful patterns for a future Forge remote surface: separate read, review-state mutation, revision writing, and deletion permissions, and avoid sending every specialized tool definition when a compact discovery operation suffices. — [Atlassian MCP Server README](https://github.com/atlassian/atlassian-mcp-server/blob/main/README.md)

### Gaps
- A host-neutral standard does not currently define how one MCP server's resource or tool result is passed to another with complete provenance. Forge must define and version its own snapshot DTO and test host behavior for large Confluence pages. — [MCP specification 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28)
- Official Atlassian documentation does not promise that every client returns identical Confluence body format, attachment handling, page-version metadata, or maximum payload size. These need live contract tests in Claude, ChatGPT, Gemini CLI, and representative coding agents. — [Atlassian MCP Server README](https://github.com/atlassian/atlassian-mcp-server/blob/main/README.md)
- It remains unknown whether target hosts can pass large peer-server results directly into a second tool call without truncation. The snapshot contract should therefore permit staged/local artifact handoff as well as inline content, but exact host limits require empirical testing. — [MCP specification 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28)

## What should Forge server own versus the host LLM, and what is the final classification?

### Takeaway
Forge should own deterministic document and review semantics; the host should own model execution, peer-server composition, user interaction, and credentials. The recommended architecture is a small stable tool boundary with optional MRTR, peer Atlassian acquisition, and a benchmarked direct Docling parser adapter.

### Cited Findings
- MCP `2026-07-28` keeps the host as the LLM application, clients as its connectors, and servers as providers of context/capabilities. Accessed 2026-09-25. — [MCP specification 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28)
- SEP-2577's rationale identifies model selection, human-in-the-loop behavior, security, and low client adoption as reasons server-initiated sampling was too complex. Accessed 2026-09-25. — [SEP-2577](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2577)
- Modern MRTR lets clients satisfy embedded model/user/root requests and retry, but it is available only under `2026-07-28`; Tasks are separate and not yet implemented by Python SDK `2.2.0`. Accessed 2026-09-25. — [Python SDK multi-round-trip requests](https://py.sdk.modelcontextprotocol.io/handlers/multi-round-trip/); [Python SDK v2.2.0 release](https://github.com/modelcontextprotocol/python-sdk/releases/tag/v2.2.0)

### Inferences
- **Forge server owns:** input validation; source adapters and immutable snapshots; parsing and normalized source blocks; page/section/asset provenance; exhaustive batching; prompt/schema construction; extraction JSON validation; quote relocation; claim/coverage ledgers; deterministic scoring, gates, deep-review mechanics, and question ordering; durable review identity/version/idempotency; revision preview/materialization; and audit/token metadata. These are the guarantees that must remain stable when the host or model changes. — [MCP specification 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28)
- **Host/LLM owns:** choosing and invoking the model; approving model requests; completing prepared extraction/advisory tasks; selecting and authenticating peer servers; retrieving Confluence content; mediating elicitation; displaying questions; approving writes; and deciding what data may leave the local machine. This matches MCP's host/client/server roles and avoids SEP-2577's failed back-channel coupling. — [MCP specification 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28); [SEP-2577](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2577)
- **ADOPT:** Official MCP Python SDK `2.2.x`, protocol `2026-07-28`, tools with structured outputs, Streamable HTTP/OAuth only for a future remote deployment, the prepare/submit inference boundary, a generic source snapshot adapter contract, Atlassian MCP as a peer, and capability-detected elicitation/MRTR convenience paths. — [Python SDK v2.2.0 release](https://github.com/modelcontextprotocol/python-sdk/releases/tag/v2.2.0); [Atlassian MCP Server README](https://github.com/atlassian/atlassian-mcp-server/blob/main/README.md)
- **BENCHMARK:** Direct Docling parser adapter versus current ingestion; Atlassian peer snapshots versus any optional direct adapter; MRTR interoperability across target hosts; and Tasks after Python SDK support lands. — [Docling MCP README](https://github.com/docling-project/docling-mcp/blob/main/README.md); [MCP Tasks extension overview](https://modelcontextprotocol.io/specification/2026-07-28/basic/utilities/tasks)
- **BORROW IDEAS:** Docling's bounded cache/configurable OCR-table pipeline and Atlassian's permission groups, auditability, least privilege, and on-demand tool discovery. — [Docling MCP README](https://github.com/docling-project/docling-mcp/blob/main/README.md); [Atlassian MCP Server README](https://github.com/atlassian/atlassian-mcp-server/blob/main/README.md)
- **NOT NEEDED:** New legacy sampling work, Roots-based filesystem discovery, embedded Docling MCP, embedded Atlassian MCP, Confluence credentials in Forge, provider SDK/API keys in MCP/core, RAG/vector infrastructure for ingestion, or mandatory resources/prompts/Tasks. — [Python SDK deprecated features](https://py.sdk.modelcontextprotocol.io/deprecated/); [Docling MCP pyproject](https://github.com/docling-project/docling-mcp/blob/main/pyproject.toml); [Atlassian MCP Server README](https://github.com/atlassian/atlassian-mcp-server/blob/main/README.md)
- **Migration sequence:** first freeze the source snapshot and prepared-inference DTOs; then add modern MRTR as a wrapper over the same service calls; then run Docling and Atlassian provenance benchmarks; only after measured gaps should Forge add an optional parser or direct source adapter. This sequence leaves current non-sampling clients working throughout. — [Python SDK multi-round-trip requests](https://py.sdk.modelcontextprotocol.io/handlers/multi-round-trip/); [Docling MCP README](https://github.com/docling-project/docling-mcp/blob/main/README.md)

### Gaps
- Target-host tests are still required for tool result size, structured-output fidelity, MRTR, elicitation, OAuth redirect handling, and peer-to-peer handoff through the host. The protocol and vendor support lists establish availability, not identical behavior. — [MCP specification 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28); [Atlassian MCP Server README](https://github.com/atlassian/atlassian-mcp-server/blob/main/README.md)
- No evidence reviewed here justifies removing Forge's current local SQLite workflow in favor of MCP Tasks; Tasks remain an extension and are not implemented in Python SDK `2.2.0`. — [MCP Tasks extension overview](https://modelcontextprotocol.io/specification/2026-07-28/basic/utilities/tasks); [Python SDK v2.2.0 release](https://github.com/modelcontextprotocol/python-sdk/releases/tag/v2.2.0)
