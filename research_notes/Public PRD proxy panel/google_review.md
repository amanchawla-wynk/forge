# Public Google Guidance Proxy Review of the MicroDrama Recommendations PRD

This is an independent synthetic proxy-expert review, prepared on 2026-09-25. It applies only publicly available Google-authored or Google-published guidance that could be substantiated. It does not claim Google endorsement, does not represent a Google review, and is not independent human validation. Public guidance from Google Cloud, Google SRE, Firebase, web.dev, Google API Improvement Proposals (AIPs), Google Play, and Google for Developers is used as a transferable benchmark, not as evidence of undisclosed internal practice. PRD page numbers refer to PDF pages, counting the first page as page 1.

## Directly Sourced External Guidance

### Takeaway

Official public Google sources support a coherent review standard: define the audience and user outcome; record consequential architecture decisions and alternatives; make API behavior complete; define measurable user and reliability objectives; pre-register experiments with primary and guardrail metrics; review privacy, security, and accessibility; and require production readiness, staged rollout, monitoring, ownership, and rapid rollback. No public source found is an official universal Google PRD template, so the standards below are a substantiated synthesis rather than a claim about a mandatory internal document format.

### Cited Findings

- **Goals, users, and required knowledge:** Google's Technical Writing course says good documentation supplies the knowledge and skills an audience needs to perform a task, recommends defining audience roles and proximity to the subject, and says a design spec should explicitly state what its audience will learn. Updated 2025-03-28. This supports requiring a PRD to identify target users/readers and the decisions or tasks the document enables, but it does not prescribe a PRD template or a mandatory “non-goals” heading. [Google for Developers, “Audience”](https://developers.google.com/tech-writing/one/audience)
- **Technical decisions and alternatives:** Google Cloud describes architecture decision records as records of important architecture decisions and their context and consequences. The page's suggested ADR structure includes status, context, decision, consequences, and considered options. This supports traceable decisions and alternatives when a PRD embeds technical design choices. The page was last reviewed 2024-09-24 according to its page metadata at access. [Google Cloud, “Architecture decision records overview”](https://docs.cloud.google.com/architecture/architecture-decision-records)
- **API design review:** Google AIP-1 defines AIPs as concise design documents and the source of truth for Google API guidance; approved AIPs are “best current practice.” It also says proposals should be grounded in prior art or concrete, well-defined use cases. Created 2018-08-20; changelog most recently updated 2025-01-09. [Google AIP-1](https://google.aip.dev/1)
- **Pagination contract:** Approved AIP-158 says collection-returning RPCs must provide pagination at the outset because adding it later is behaviorally backward-incompatible. It specifies `page_size`, `page_token`, `next_page_token`, unchanged request parameters across pages, and the sole end-of-collection signal. Created 2019-02-18; changelog updated 2025-07-08. [Google AIP-158](https://google.aip.dev/158)
- **Errors:** Approved AIP-193 requires standardized, machine-readable errors and says human-readable error messages should be brief, understandable, and actionable without assuming expertise in the implementation. Created 2019-07-26; major clarity update 2024-10-18. [Google AIP-193](https://google.aip.dev/193)
- **Measurable reliability:** Google Cloud says reliability should be defined from user-experience goals and translated into service-level indicators and objectives for critical user journeys. Last reviewed 2024-12-30. [Google Cloud, “Define reliability based on user-experience goals”](https://docs.cloud.google.com/architecture/framework/reliability/define-reliability-based-on-user-experience-goals)
- **Observability:** Google Cloud's reliability guidance calls for telemetry that can reveal potential failures and for monitoring aligned with user-facing reliability goals. Last reviewed 2024-12-30. [Google Cloud, “Detect potential failures by using observability”](https://docs.cloud.google.com/architecture/framework/reliability/observability)
- **Graceful degradation:** Google Cloud recommends designing workloads to preserve essential functionality when components fail, including identifying dependencies and degradation behavior. Last reviewed 2024-12-30. [Google Cloud, “Design for graceful degradation”](https://docs.cloud.google.com/architecture/framework/reliability/graceful-degradation)
- **Launch readiness:** Google's published SRE launch checklist covers an architecture sketch; traffic and capacity estimates; load and end-to-end tests; dependency failure behavior; backup/restore and disaster recovery; monitoring and alerts; security review; release and change control; canaries; staged rollout; external dependencies; and operating procedures. It is explicitly the original checklist circa 2005 and appears in the 2017 SRE book, so it is useful public precedent but not a current universal mandate. [Google SRE, “Launch Coordination Checklist”](https://sre.google/sre-book/launch-checklist/)
- **Rollout and rollback:** Google's SRE launch chapter says almost all service updates proceed gradually with verification steps; it describes canaries, automatic rollback when validation fails, and feature-flag systems that can independently revert each change immediately. Published in the 2017 SRE book. [Google SRE, “Reliable Product Launches at Scale”](https://sre.google/sre-book/reliable-product-launches/)
- **Ownership:** The same SRE chapter says a launch plan should identify launch actions and who is responsible for each item, and that manual processes should be documented so any team member can execute them in an emergency. Published 2017. [Google SRE, “Reliable Product Launches at Scale”](https://sre.google/sre-book/reliable-product-launches/)
- **Experiment design:** Firebase A/B Testing documentation requires an objective metric and supports additional metrics for broader impact; it warns that experiments need enough users and time, reports probability and confidence information, and recommends acting only after results are meaningful. The page was current when accessed 2026-09-25; no publication date was exposed in the fetched page. This is product documentation for Firebase, not a universal Google experimentation policy. [Firebase, “About Firebase A/B tests”](https://firebase.google.com/docs/ab-testing/ab-concepts)
- **Pre-production validation:** Google Play recommends beginning with an internal test, expanding to a smaller closed group, and then using open testing; the purpose is to fix technical or user-experience issues before production and collect feedback through an explicit channel. The help page displays copyright 2026 but no article update date. [Google Play Console Help, “Set up an open, closed, or internal test”](https://support.google.com/googleplay/android-developer/answer/9845334)
- **Privacy and compliance:** Google Cloud's security pillar says privacy and regulatory needs should be identified, data should be classified, and controls should reflect data sensitivity and lifecycle obligations. Last reviewed 2025-02-05. [Google Cloud, “Meet regulatory, compliance, and privacy needs”](https://docs.cloud.google.com/architecture/framework/security/meet-regulatory-compliance-and-privacy-needs)
- **Privacy-preserving personalization:** Google's public Privacy Sandbox material describes privacy by default, limiting tracking, and a private-compute approach to personalization without sharing identifying user data. Updated 2025-10-24. It demonstrates a public privacy direction but does not require this architecture for unrelated recommendation products. [Privacy Sandbox, “Privacy protections”](https://privacysandbox.google.com/protections)
- **Accessibility:** Google's web.dev accessibility course says products should be designed and built so people with disabilities can interact in a meaningful and equivalent way, and includes measurement, automated testing, manual testing, assistive-technology testing, focus, color/contrast, motion, touch, and cognition. The course is evergreen; the fetched landing page did not expose one course-wide update date. [web.dev, “Learn Accessibility”](https://web.dev/learn/accessibility/)
- **Change management:** Google Cloud recommends controlled, automated changes, validation, and rollback practices. Last reviewed 2024-10-31. [Google Cloud, “Automate and manage change”](https://docs.cloud.google.com/architecture/framework/operational-excellence/automate-and-manage-change)

### Inferences

- A defensible proxy rubric can require explicit goals, non-goals, user needs, success measures, architecture/API contracts, experiment criteria, privacy/security/accessibility treatment, reliability and launch gates, rollback, and ownership. The specific requirement wording should be generic and evidence-oriented rather than presented as “Google's PRD template.”
- “Non-goals” are useful to constrain scope, but the public Google sources reviewed substantiate context, decisions, alternatives, and scope more directly than a mandatory non-goals section. A rubric should accept equivalent explicit scope exclusions.
- Product metrics and reliability metrics are different. A launch can improve CTR while harming crashes, latency, completion, retention, content safety, accessibility, or user control; the public sources support objective and additional metrics plus user-journey SLOs.

### Gaps

- No official public Google source located defines a single, universal PRD schema covering all requested categories.
- No official public Google source located states that every product must use the HEART framework. The well-known HEART paper could not be reliably retrieved from the current Google Research URL, so no HEART-specific requirement is asserted here.
- Material Design pages were not needed to substantiate the core accessibility finding because web.dev provides directly accessible Google guidance; this review does not claim a Material-specific launch requirement.

## Quote- and Page-Backed PRD Review

### Takeaway

The PRD contains substantial ranking logic, event fields, phased sources, content filters, and several fallbacks. It is not implementation-ready as a controlling launch document because core behavior contradicts itself, critical prerequisites remain unresolved, the experiment has no valid decision framework beyond CTR, and privacy, accessibility, reliability objectives, release gates, rollback, and accountable launch ownership are absent. These are document defects, not a judgment that linked teams or linked design documents have done no work.

### Cited Findings

#### Implementation-Blocking Defects

1. **No user problem, user need, or measurable product goal is defined.** The overview says only: “This document consolidates all product, data, and ML requirements for the MicroDrama recommendation system on XstreamPlay app” and that it covers “three products going live in MVP” (p. 1). The closest claimed outcomes appear much later as unsupported assertions: “Reduces cognitive load,” “Maintains mood,” and “Increases CTR” (p. 20). There is no baseline, target population, target value, horizon, or evidence connecting the proposed ranking to those outcomes. This blocks prioritization and makes acceptance subjective.
2. **Launch scope and serving source conflict.** The PRD says the manual collection remains the source of truth “till the ML and Analytics team is ready ... (timeline : 30-60 days post MVP launch)” (p. 3), but also says the MAB uses signals “from the D0 for all users” (p. 4), lists “Source 1 : ML MAB ... All users from D0” (p. 9), and places MAB in “MVP-Phase 1.0 / Launch day” (p. 14). Page 1 separately labels “Recommended Feed Contentby ML model(4-5 weeks from launch)” as MVP Phase 2. These statements do not produce one implementable launch configuration.
3. **Skip boundaries and tier semantics are contradictory or mathematically impossible.** The ranking defines “Soft Skipped Contents(21secs>=X>=40secs)” and “Hard Skipped Contents(>=5 secs)” (p. 7), while the formal table defines hard as “watch duration ≤ 5secs,” medium as “6 secs ≤ watch duration < 20 secs,” and soft as “20 secs ≤ watch duration < 50 secs” (p. 9). The backlog repeats “Soft Skipped Contents(21secs>=X>=40secs)” but changes hard to “<=5 secs” (p. 18). The worked example labels 2-, 3-, and 4-second hard skips “Tier 1” (pp. 10-11), whereas the table labels hard skip “Tier 3” (p. 9). Engineers cannot derive deterministic classification or placement from these definitions.
4. **The mood-picker state window conflicts.** The primary flow says an explicitly selected mood is “Not using this mood outside the same session” (p. 5). The ML-down fallback instead uses “Explicitly Selected Mood Contents if any mood has been selected in last 30 days window” (p. 16), and event storage is specified for a “rolling 30 days” (p. 11). The PRD does not state whether the latter is an exception, a later phase, or superseding behavior.
5. **Critical launch prerequisites remain undecided or unimplemented.** Metadata says `content_type : To be decided by Supply` (p. 1). The launch callouts say the genre mapping “Must be built and validated,” all-season parent mapping “needs to be done,” the erotic flag is necessary because “Without this, erotic content cannot be excluded,” the parental-control flag is necessary because “Without this, A-rated content cannot be filtered,” and Like/Dislike “must be added” because otherwise signals cannot be read in real time (p. 8). These are explicit unmet preconditions for ranking correctness and content safety, but no go/no-go gate, due date, approver, or fallback is attached.
6. **The feed API contract is incomplete and internally inconsistent.** The PRD says only “Pagination support for MD contents is needed after every 10 contents” and “The client calls will happen on the 7th/8th contents” (p. 8), but provides no cursor/token semantics, consistency rule during intra-session reranking, terminal condition, idempotency, retries, timeout, or errors. It also describes event payloads with `genre_tags[]` (p. 11) while the field table types `genre_tags` as `string` (p. 12). A linked “API Doc” appears on p. 2, but the PRD neither imports its controlling requirements nor identifies a version/status; this PDF alone cannot establish a testable contract.
7. **The experiment decision rule is not sufficient to launch or promote safely.** The only concrete experiment gate is: “A/B test: measure CTR improvement vs control (rule-based only). Promote MAB if CTR +5% vs control” (p. 15). The document does not define CTR numerator/denominator, assignment unit, eligible population, sample-size/power, duration, novelty handling, confidence/error criterion, exposure logging, mutually exclusive variants, stopping rule, or guardrails for watch quality, retention, latency, errors, safety, or complaints. Earlier statements merely say “A/B Experimentation would be needed” (p. 5) and “create experiment variants” (p. 4).
8. **Data collection lacks a privacy/security lifecycle.** The design requires `user_id`, `session_id`, detailed watch percentage/duration, feed position, genres, language, and timestamp, with DP storing per-user/session state for a “rolling 30 days” (p. 11). It also relies on a “Persistent persona store” and derives a MicroDrama persona from continue-watching, likes, and skips (pp. 20-21). The PRD gives no purpose-by-field justification, notice/consent or lawful-basis decision, access controls, encryption expectations, deletion/user-rights path, retention for the persistent persona, de-identification, regional handling, abuse/threat analysis, security reviewer, or privacy launch gate.
9. **Accessibility is not specified for a blocking, repeatedly triggered interaction.** The picker can be shown after “N=3 consecutive hard skips,” shown again after 10, and up to twice in a user lifecycle (p. 10). The appendix calls one intervention “blocking but still quick” (p. 19). No requirement covers screen-reader semantics, focus order/return, keyboard or switch access, touch target, contrast, text scaling, motion/autoplay alternatives, captions, cognitive load, dismissal, or accessibility testing. This is launch-relevant because the picker and vertical autoplay feed are core user journeys, not incidental UI.
10. **Reliability has fallbacks but no objective or validated operational contract.** The PRD specifies “When ML services is down(~0.001% chances)” use a curated/persona fallback (p. 16) and “PersonaIQ / Watch History down Fall back to the curated collection” (p. 17). The `~0.001%` assertion has no source or time window. There are no availability/latency/freshness SLOs, capacity estimates, load tests, timeouts/retries/circuit breaking, observability and alerts, fallback quality threshold, dependency owners, incident runbook, or recovery test. “Increase Aerospike connections” appears only as backlog (p. 18), underscoring unresolved capacity work.
11. **There is no production rollout, rollback, or acceptance plan.** The document supplies calendar phases, for example “1-2 weeks post-launch,” “3-4 weeks post-launch,” and “8–12 weeks post-launch” (pp. 14-15), but no canary/staged percentages, pre-launch test stages, entry/exit criteria, stop conditions, kill switch, rollback trigger, rollback owner, or validation window. “MAB Model will run in parallel with rule-based ranking” (p. 15) could enable a safe shadow/experiment path, but the operational procedure is not specified.
12. **Ownership is partial and not sufficient for launch.** Page 19 assigns owners and priorities to three open points, such as “ML + Product / P0” for genre mapping and “Product + BE / P1” for language fallback. Elsewhere, responsibilities are team-level statements such as “Curation team to create and maintain” (p. 3), “DP needs to store” (p. 11), and “developed by the Analytics & DP team” (p. 8). There is no directly responsible launch owner, approver, experiment owner, on-call/incident owner, privacy/security/accessibility reviewer, dependency acceptance, or dated closure plan.
13. **The document has no authoritative precedence/version rule despite later edits.** “Technical Solutioning - Latest as on 29th June 2026” and a later “BACKLOG” define a new rung order (p. 18), while earlier pages retain conflicting orders (pp. 7-9, 12, 16-17). Strike-throughs show some revision history (p. 10), but no statement says whether the backlog supersedes earlier requirements. Implementation teams could reasonably choose different “latest” rules.

#### Hard Negatives: Areas That Are Adequate or Materially Present

- **Scope is not wholly absent.** The PRD enumerates the MVP products on p. 1 and explicitly marks “Product 5 - New in your language(out of scope in MVP)” (p. 13). The issue is inconsistent phase boundaries, not a total lack of scope.
- **User cohorts are defined.** “Existing User” means a user who “Has streamed ≥1 content,” and “Cold Start User” is the remainder (p. 4). More segmentation may be useful, but it would be incorrect to say the PRD has no user definitions.
- **Core recommendation behavior is unusually detailed for a PRD.** It defines language and genre priority cascades (pp. 5-7), interaction-state ordering (pp. 7-8), a concrete sorting example (p. 8), player-end journeys (p. 12), and model progression (pp. 13-15). The defect is contradiction and acceptance ambiguity, not lack of algorithmic detail.
- **Event instrumentation is substantially present.** The PRD names `playback_progress`, `scroll_skip`, and `item_impression`, plus trigger and payload fields (pp. 11-12), and provides a signal/source/storage/cadence table (pp. 20-21). It needs governance, schema resolution, and experiment exposure/quality events; it is not fair to label instrumentation entirely missing.
- **Fallback behavior is present for important dependencies and exhaustion states.** Pages 16-17 cover trope exhaustion, ML-service outage, PersonaIQ/watch-history outage, and entire-catalog interaction. This is a meaningful reliability strength even though thresholds, validation, and operations are missing.
- **Content-safety filtering is explicitly recognized.** The PRD requires erotic-content metadata and a parental-control flag (p. 8), and states the final behavior as “exclude A-rated content” and remove erotic content from recommendation pools (p. 21). The blocker is prerequisite closure and testability, not absence of safety intent.
- **Future model stages have data prerequisites.** The phase table identifies data needed for rule-based, MAB, content-based, and collaborative models (pp. 14-15). The numerical collaborative-filtering threshold may need validation, but model progression is not unspecified.
- **Some open issues have owner and priority fields.** The Phase 2 table assigns team owners and P0/P1 priority to genre mapping, catalog depth, and TTMK language handling (p. 19). The criticism should remain limited to incomplete launch-wide accountability.

#### Scoped Alternatives and Non-Issues

- **Variant 1 versus Variant 2 is not itself a contradiction.** Page 4 explicitly labels two future “Handling Scenarios” and page 4 also asks for experiment variants. They are alternative source-merging strategies. The real missing requirement is assignment and decision criteria, not forced reconciliation into one algorithm before the experiment is designed.
- **Rule-based and MAB ranking can coexist.** Page 15 explicitly says “MAB Model will run in parallel with rule-based ranking.” This can be a valid control/treatment or fallback design. The conflict is only whether MAB is actually launch-day serving for all users versus delayed 30-60 days.
- **Product 1 and Player End may legitimately use different priority order.** Product 1 is a personalized discovery feed (pp. 4-8); Product 2 begins with a seed and five same-genre/language recommendations (pp. 12-13). Different ranking sequences are scoped by surface and should not be treated as a defect unless shared behavior is claimed.
- **Phase 2 annexure items are not launch requirements merely because they appear later.** The p. 19 table labels P2/P3/P4 as Phase 2. They should remain out of the launch blocker list unless another passage claims they are D0 dependencies.
- **The new-language product is a clear non-goal, not an omission.** It is explicitly out of MVP scope due to limited language variation (p. 13). However, the TTMK fallback remains a documented open point (p. 19), so baseline language behavior still needs closure.
- **A later backlog can legitimately revise an earlier design.** Page 18 may represent intended supersession. The defect is document control: without an explicit precedence statement, readers cannot safely infer that all earlier tables are obsolete.

### Inferences

- **Overall proxy verdict:** not implementation-ready as the sole controlling PRD. The immediate blockers are deterministic behavior conflicts, unresolved safety/API prerequisites, missing experiment validity, and missing release/privacy/accessibility/reliability gates.
- The smallest credible remediation is not more algorithm prose. It is an authoritative D0 requirements table, closure of prerequisites, one normalized skip/state taxonomy, a versioned API contract, a metric/experiment contract, and a launch checklist with owners and rollback.
- Linked Figma, API, ML, DP, and HLD documents may contain missing evidence. Because the assignment is to review this PDF, links are evidence that dependencies exist, not proof that their requirements are complete, approved, current, or mutually consistent.

### Gaps

- The linked private documents and systems could not be authenticated or reviewed. Findings do not assert that work is absent outside the PDF.
- The PDF exposes no formal approval history, document owner, or revision log beyond inline dates and strike-throughs.
- Business baselines, traffic forecasts, incident history, legal jurisdiction, supported assistive technologies, and organizational SLO standards were not available, so this review cannot propose product-specific numeric thresholds.

## Proposed Generic Rubric Requirements

### Takeaway

The following additions are reusable across products because they evaluate decision completeness, testability, user protection, and production readiness rather than this PRD's domain terms. They should be scored on evidence present in the PRD or explicitly incorporated versioned artifacts, and should allow “not applicable” only with a rationale.

### Cited Findings

1. **Problem, users, and outcomes:** “The document identifies target users, the user need/problem or opportunity, current baseline/evidence, desired outcome, and why the work is valuable.” This follows Google's audience/task guidance and user-experience-oriented reliability guidance. [Google Technical Writing](https://developers.google.com/tech-writing/one/audience); [Google Cloud reliability](https://docs.cloud.google.com/architecture/framework/reliability/define-reliability-based-on-user-experience-goals)
2. **Goals, non-goals, and phase boundaries:** “The document states measurable goals and explicit exclusions or equivalent scope boundaries, and maps each requirement to a release phase.” This is a generic control against scope ambiguity; Google SRE's launch process emphasizes a concrete launch plan and scoped risk. [Google SRE launch chapter](https://sre.google/sre-book/reliable-product-launches/)
3. **Authoritative decisions and alternatives:** “Consequential product/architecture choices record context, selected option, alternatives considered, consequences, status, and supersession/precedence.” [Google Cloud ADR guidance](https://docs.cloud.google.com/architecture/architecture-decision-records); [Google AIP-1](https://google.aip.dev/1)
4. **Unambiguous behavioral specification:** “Rules, thresholds, units, boundaries, priority, state transitions, tie-breakers, and examples are internally consistent and yield one result for every supported input.” This is a general testability requirement; approved AIPs illustrate precise normative contracts. [Google AIP-158](https://google.aip.dev/158)
5. **Versioned interface contract:** “Every changed interface specifies request/response schema, types/nullability, identifiers, pagination/streaming, ordering and consistency, auth, errors, retries/timeouts, compatibility/versioning, and owner, or incorporates a versioned approved contract.” [Google AIP-158](https://google.aip.dev/158); [Google AIP-193](https://google.aip.dev/193)
6. **Success metric contract:** “Each goal has a metric with exact definition, baseline, target/delta, population, data source, attribution window, segment cuts, and decision owner; counter-metrics protect user and system quality.” Firebase's experiment docs substantiate objective plus additional metrics, while Cloud reliability guidance substantiates user-journey measures. [Firebase A/B Testing](https://firebase.google.com/docs/ab-testing/ab-concepts); [Google Cloud reliability](https://docs.cloud.google.com/architecture/framework/reliability/define-reliability-based-on-user-experience-goals)
7. **Experiment validity:** “Experiments specify hypothesis, control/treatments, randomization and assignment unit, eligibility/exclusions, exposure logging, sample-size or precision rationale, duration, statistical decision rule, novelty/peeking handling, guardrails, stop conditions, and promotion/rollback criteria.” [Firebase A/B Testing](https://firebase.google.com/docs/ab-testing/ab-concepts)
8. **Privacy and data governance:** “For every personal or sensitive signal, the document defines purpose, necessity/minimization, classification, notice/consent or legal review, retention/deletion, access, security controls, sharing/region constraints, user controls, and accountable reviewer.” [Google Cloud privacy guidance](https://docs.cloud.google.com/architecture/framework/security/meet-regulatory-compliance-and-privacy-needs); [Privacy Sandbox protections](https://privacysandbox.google.com/protections)
9. **Security and abuse:** “The document identifies assets, trust boundaries, authentication/authorization, misuse and abuse cases, rate limits, secrets, auditability, threat/security review, and required mitigations.” Google's public launch checklist explicitly calls for security design review, authentication, access control, and abuse-related controls. [Google SRE launch checklist](https://sre.google/sre-book/launch-checklist/)
10. **Accessibility acceptance:** “Core journeys identify applicable accessibility requirements and include measurable acceptance and test coverage using automated checks, manual keyboard/focus checks, and representative assistive technologies; motion, media, touch, cognition, text scaling, contrast, and localization are considered where relevant.” [web.dev accessibility course](https://web.dev/learn/accessibility/)
11. **Reliability and dependency behavior:** “Critical journeys have SLIs/SLOs or equivalent availability, latency, correctness, and freshness targets; each dependency has timeout/retry/degradation behavior, capacity assumptions, and tested recovery.” [Google Cloud reliability](https://docs.cloud.google.com/architecture/framework/reliability/define-reliability-based-on-user-experience-goals); [graceful degradation](https://docs.cloud.google.com/architecture/framework/reliability/graceful-degradation); [Google SRE launch checklist](https://sre.google/sre-book/launch-checklist/)
12. **Observability and operations:** “The document identifies telemetry, dashboards, alerts, data-quality checks, on-call/runbook ownership, incident paths, and validation of end-to-end user behavior.” [Google Cloud observability](https://docs.cloud.google.com/architecture/framework/reliability/observability); [Google SRE launch checklist](https://sre.google/sre-book/launch-checklist/)
13. **Launch gates and rollback:** “The release plan specifies pre-production testing, prerequisite closure, canary/staged cohorts, verification windows, go/no-go approvers, stop/rollback triggers, kill switch or reversible mechanism, rollback owner, and post-launch review.” [Google SRE launch chapter](https://sre.google/sre-book/reliable-product-launches/); [Google Play testing guidance](https://support.google.com/googleplay/android-developer/answer/9845334); [Google Cloud change management](https://docs.cloud.google.com/architecture/framework/operational-excellence/automate-and-manage-change)
14. **Ownership and dependency acceptance:** “Every launch-critical requirement, external dependency, manual process, decision, and unresolved issue has one accountable owner, status, due date, and approver/acceptance evidence.” [Google SRE launch chapter](https://sre.google/sre-book/reliable-product-launches/)
15. **Evidence and hard-negative discipline:** “Reviewers must cite exact document evidence, credit requirements that are materially present, distinguish phase/surface alternatives from contradictions, and label external links as unverified unless their version and approval are incorporated.” Google's SRE chapter warns that checklist intent must be applied to the launch rather than mindlessly applying every concrete question. [Google SRE launch chapter](https://sre.google/sre-book/reliable-product-launches/)

### Inferences

- These requirements should be criterion-level and reusable. Product-specific examples such as “skip tier,” “MAB,” “mood picker,” “MicroDrama,” “CTR +5%,” or named internal systems should not enter the generic rubric.
- Scoring should separate **present**, **partial**, **missing**, **contradictory**, and **not applicable with rationale**. A long document with conflicting rules should not receive full credit merely because each topic is mentioned.
- Linked artifacts should count only when the PRD identifies an immutable/versioned artifact, its status or approval, and which requirements it controls. A bare hyperlink is discoverability, not verified completeness.
- Safety-critical prerequisites should be gated rather than averaged into a total score. Examples include content eligibility controls, privacy/security approval, inaccessible core journeys, non-reversible launches, and undefined behavior at rule boundaries.

### Gaps

- Numeric rubric weights and blocking thresholds require calibration against real PRDs and independent human labels; this synthetic review cannot provide that validation.
- Organization-specific legal, security, accessibility, experimentation, and SLO policies should override these public proxy requirements where stricter or more precise.
- Public Google guidance varies in age and scope: the SRE checklist is historical, Firebase is product-specific, AIPs govern APIs, and web.dev is web-focused. The rubric should preserve the principle behind each source and avoid claiming universal Google policy.
